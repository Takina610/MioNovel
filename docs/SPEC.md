# MioNovel 设计说明

这份文档记录的是**为什么这么做**。代码能告诉你它怎么运行，但告诉不了你当初为什么否掉另一种做法——
过几个月你要加功能时，那些理由比代码更值钱。

README 讲怎么跑和怎么用，这份讲决定与理由。

---

## 一、定位

本地优先的小说阅读 PWA。导入自己的 txt / epub，存在浏览器的 IndexedDB 里，离线可读，没有后端、没有账号。

三个前提决定了后面几乎所有选择：

1. **本地是唯一副本。** 所以原始文件必须原样存着（能导出、能重新解析），并且要申请持久化存储。
2. **用户的书是五花八门的。** 中文老 txt 是 GBK、繁体是 Big5、epub 是别人用什么工具生成的都有。
   解析层的第一目标是「尽量读懂」，第二目标才是「读得快」。
3. **要长期阅读，不是看一次。** 排版、主题、进度恢复的体验比功能数量重要。

---

## 二、技术选型

| 选择 | 理由 |
|---|---|
| Vite + React + TS | 与同目录的 MioNote 保持一致，同一套工具链 |
| Dexie 4 | 类型化的 IndexedDB 封装；`useLiveQuery` 让书架自动跟着数据变，不需要手动 invalidate |
| zustand + persist | 阅读设置只有几百字节，localStorage 够用；书和章节进 IndexedDB |
| Tailwind CSS v4 | CSS-first，`@theme inline` 能把语义 token 直接接到工具类上——这是主题系统的基础 |
| fflate | 零依赖的 zip。替代 jszip：EPUB 只需要「一次解出一个 ArrayBuffer 里的所有条目」，fflate 更小更快 |
| chardet | 纯 JS 的编码识别，零运行时依赖 |
| dompurify | 属性白名单、URL 校验、mXSS 这些深水区交给它（但见第七节的第二层说明） |
| vite-plugin-pwa | Workbox 封装，precache app 外壳就够 |
| **不用** epub.js | 见下 |

### 2.1 为什么不用 epub.js（2026-09-22 决定）

原本的计划是用 epub.js，最后改成了自研解析。改变主意的不是「epub.js 不好用」，而是两件事：

**一是 koodo-reader 的实际做法。** 它是这个领域最成熟的开源阅读器，而它的依赖表里**没有 epubjs**。
它自己写了一个 EPUB 引擎（`kookit`，以 533KB 压缩产物 vendored 进仓库），里面的 book 对象刻意模仿了
epub.js 的数据结构（`manifest` / `spine` / `sections` / `toc` / `resolveHref`），底层用 JSZip 解包。
换句话说：最需要它的人，最后选择了重写。

**二是它的价值集中在 iframe 上，而 iframe 正好挡住我们要的东西。** epub.js 的核心是 `Rendition`，
它把正文渲染进一个 iframe——分页、CFI、主题 API 都建立在这个前提上。而 CSS 自定义属性不跨 iframe 边界，
于是主题要么注入第二份（在 iframe 里重新拼 CSS 字符串），要么维护两套。epub.js 的依赖树也不小：
`jszip + lodash + core-js + localforage + path-webpack`，而且版本停在 2023 年。

自研解析的代价大约 300 行（目录、图片路径重写、封面回退链、spine 归并），换来的是：

- 一套排版：TXT 和 EPUB 走同一组 CSS，因为都归一化成「章 HTML」；
- 一套主题：变量直接级联到正文，不需要第二份 CSS；
- 一套进度：章序号 + 章内比例，两种格式通用；
- 没有 iframe：划词、注解、全文搜索这些后续功能的门是开着的。

**这条决定是可逆的。** `parsers/types.ts` 里的 `BookParser` 接口就是为它留的：想把 EPUB 换成 epub.js，
写一个实现注册进去即可，数据层和阅读器不用动。

### 2.2 参考 koodo-reader 的许可边界（重要）

koodo-reader 与它的渲染引擎 kookit 都是 **AGPL-3.0**（`package.json` 里没有 license 字段，以 LICENSE 文件为准）。

本项目**只借鉴架构思路，代码全部自己写**，没有从它那里复制任何代码。借鉴的是三个想法：
每本书独立的解析规则与「改规则后重新解析」、每本书独立的样式设置、自定义 CSS 逃生口——
这三个都用我们自己的方式实现（见 `BookPanel.tsx`、`store/settings.ts`）。

明确**没有**借鉴的是它的主题系统与安全模型：它没有 CSS 变量、没有主题对象、没有注册表，
判断暗色靠把背景色和字面量 `"rgba(44,47,49,1)"` 做字符串相等比较；正文净化依赖单一机制。
这两处恰好是本项目要做对的对方（第五、七节）。

## 三、分层：解析 → 存储 → 渲染

```
文件 → [解析层] parsers/ → ParsedBook → [存储层] db/ → [渲染层] 阅读器
        每格式一个实现      归一化模型      Dexie      只认归一化模型
```

`BookParser` 是整个应用的契约：

```ts
interface BookParser {
  format: BookFormat
  detect(head: Uint8Array, fileName: string): boolean   // 看 magic bytes，不信后缀
  probe(file: File, options): Promise<FileProbe>        // 便宜地看一眼
  parse(file: File, sink: ParseSink, options): Promise<ParsedHead>
}
```

两个约定值得单独说：

**一、章节通过 `sink.onChapter()` 逐章交出去，解析器自己不保留全书。** 这是「30MB 的 txt
峰值内存只有单章 + 一个解码缓冲」的前提。如果把 `ParsedChapter[]` 作为返回值，解析器就必须把整本书
留在内存里，大文件会直接把标签页撑爆——koodo-reader 的 TXT 路径就是那样：全量 decode →
`split("\n")` 整个行数组 → 再拼成整个 HTML 字符串。

**二、`BookParser` 按需加载。** txt 和 epub 的解析要用到 chardet / fflate / dompurify（约 90KB），
而打开书架、读一本已经导过的书完全不需要它们。做成动态 `import()` 之后，主包从 182KB 降到 150KB（gzip）。
连 `MANUAL_CHARSETS` 都单独放在 `charsets.ts`（不依赖 chardet），就是为了不让书架上的一个编码下拉框
把编码检测库拉进主包。

## 四、数据层

### 4.1 为什么是五张表而不是一张

```
books      id / 元数据 / 进度 / 章数与字数前缀和 / 卷分组节点
files      bookId, 原始文件 Blob（原样）
chapters   [bookId+index], 章节 HTML
toc        [bookId+index], 只有标题、层级、字数
resources  [bookId+path], epub 里抽出的图片
```

- **`files` 与 `books` 分开**：书架渲染时整表读 `books`，如果原始文件也在里面，几十 MB 会被顺手反序列化出来。
- **`toc` 与 `chapters` 分开**：目录抽屉需要**全部**章节的标题，而 `chapters` 每行都带着那一章的完整 HTML。
  一本 3000 章的书整表读出来是十几 MB，只为了拿 3000 个标题；`toc` 把这份代价压到几百 KB。
- **`resources` 单独存图片**：章节 HTML 里图片是 `mnres://` 占位，渲染当前章时才取出来换成 ObjectURL，
  离开就 revoke。打开一章完全不碰 epub 原文件，内存占用只跟当前章有关，跟书有多大无关。

对照：koodo-reader 用 localforage 存**五个巨大的数组**，每次保存一条笔记都要读出整个数组、改完再写回去；
封面 base64 内联在 `books` 数组里；阅读进度存在 localStorage。这三条我们都避开了。

### 4.2 进度模型

```ts
progress = { chapterIndex, ratio }      // ratio 是章内比例 0-1
```

全书百分比靠导入时算好的 `charOffsets`（每章起始字数的前缀和）O(1) 算出：

```
已读字数 = charOffsets[i] + (charOffsets[i+1] - charOffsets[i]) * ratio
```

滚动模式的 ratio 来自 `scrollTop / (scrollHeight - clientHeight)`，翻页模式来自 `(page+1) / totalPages`。
两种模式、两种格式存的是同一个量，所以切换阅读模式或重新解析都不会让进度错位，也不需要格式专属的定位字段。

**章节字数只数正文，不数我们自己包上去的 HTML 标签**——否则段数多的书会被系统性高估，百分比跟着偏。
这个 bug 在写 TXT 解析时出现过一次（`countChars(html)` 把 `<p></p>` 也算进去了）。

### 4.3 导入流水线

```
1. 签名去重（name + size + lastModified）
2. 判定格式 → 按需加载解析器
3. probe：编码、将采用的分章规则、前几个章标题
4. **先落盘**：写 books（state: 'importing'）+ files
5. 解析，章节按 50 章一批 bulkAdd
6. 成功 → state: 'ready' + 章数/字数/前缀和/卷分组；失败 → state: 'error' + 中文原因
```

**先落盘再解析**是关键：中途失败或浏览器崩溃都不会丢原始文件，用户可以重试或改规则重新解析，
不用再拖一次文件。启动时的 `cleanupStaleImports()` 会把上次崩溃留下的 `importing` 记录收尾成 error
（靠内存里的 `inFlight` 集合区分「残留」和「这次正在跑的」）。

**二进制内容在导入这一步就被拒掉。** 判断只看内容不看后缀：随机字节、损坏的 epub、pdf
用 GB18030 也能解出「东西」，但那是一屏乱码，收进书架只会得到一本读不了的书。
所以解码之后先确认样本像不像文本（控制字符比例），不像就报「这个文件读不出文字」。
空文件放行（那是合法输入，后面会给一章「（空文件）」）。

**失败一定要看得见。** 探测阶段就失败的（内容不是文本、格式判定不出来）不会有书记录，
书架上也就没有卡片可以显示错误——这种失败改成一次性提示，并把任务从队列里清掉。

**没有导入前的确认弹窗。** 识别结果写进书里，书架上直接显示解析后的样子，觉得不对就在「解析设置」里改，
改完原地重新解析——比让用户在没看到结果之前先确认编码合理。

## 五、主题系统

### 5.1 做法：注册表是唯一事实来源，切换只改一个属性

```ts
interface ReaderTheme { id, name, scheme: 'light'|'dark', builtin, tokens }
```

`apply.ts` 遍历注册表，把每套主题编译成一段 `:root[data-theme='…'] { --mn-bg: …; }`，
拼成一张 `<style id="mn-theme">` 注入 `<head>`。换主题就是改 `documentElement.dataset.theme` 一个属性。

带来三件事：

1. 换主题不触发 React 渲染，也没有逐 token 的 JS 写入，浏览器只是换了一条 CSS 规则；
2. 用户主题（以后的主题编辑器、导入的主题）只要注册进 registry 就自动生效，不需要改代码或 CSS；
3. 加一套主题的成本 = 加一条数据。

`styles/app.css` 里用 Tailwind v4 的 **`@theme inline`** 把语义 token 接上：

```css
@theme inline { --color-bg: var(--mn-bg); … }
```

必须用 `inline`：值是 `var()` 引用，`inline` 才会把值内联进工具类（`bg-bg` → `background-color: var(--mn-bg)`）。
不用 `inline` 的话 Tailwind 会先在 `:root` 里把 `--color-bg` 固化成当时的颜色，运行时换主题就换不动了。
接上之后，书架、工具栏、弹窗、正文全部走同一组变量——换主题是整个 app 一起变，不会只换一半。

### 5.2 为什么不做成「组件里传 props / 写内联样式」

这是 koodo-reader 的做法，也是我们要避免的：它没有 CSS 变量，一个「主题」是两个裸字符串
（`{ key, textColor, backgroundColor, title }`），有四套并行机制——强调色生成 CSS 打在约 60 个
**手工维护的选择器数组**上、明暗皮肤靠换整个 `<link>` 样式表、阅读区用 React 内联样式、
正文 iframe 里注入拼接的 CSS 字符串。每加一个可主题化的界面，就要往那些数组里补类名。

变量级联不需要这个成本：新界面只要用现成的工具类就自动跟随主题。

### 5.3 阅读设置走同一套思路

字号、行距、字距、首行缩进、段间距、栏宽、对齐、字体栈都是 CSS 变量，写在阅读器容器上：

```
--mn-font-size / --mn-line-height / --mn-para-gap / --mn-indent / --mn-content-width / …
```

改动只是对一个元素 `style.setProperty`，正文 DOM 不重渲染，变量级联到从 EPUB 迁进来的 HTML 上。
这也是「一套排版管两种格式」能成立的原因：TXT 生成的 `<p>` 和 EPUB 迁进来的 XHTML 走同一组规则。

### 5.4 主题可以声明「形态」：编辑器那一套（2026-09-23）

有两套主题（`vscode` / `vscode-light`）带了一个字段：

```ts
chrome?: 'plain' | 'code'   // 不写就是 plain
code?: CodeTokens           // 行号 / 缩进线 / 对话 / 注释 / 标题 / 数字
preset?: Partial<ReaderSettings>
```

`chrome: 'code'` 时，外壳换成代码编辑器：书架变成资源管理器（书是文件夹、章是文件）、
正文按代码排版（行号、语法配色、缩略图）、下面一条状态栏。**颜色仍然只有主题那一份**，
形态是主题的一条数据——不是另开一个「编辑器模式」开关。理由是用户要的是「选中这套主题，
整个应用就是那个样子」；拆成两个开关，颜色和形态可以互相矛盾，那不是一种观感，只是两块设置。

由此多了三条约束：

1. **组件不认主题 id，只认 `chrome`**（`hooks/useTheme.ts` 的 `useChrome()`）。CSS 那边同理：
   `styles/code.css` 里所有规则都挂在 `.mn-code` 这个类下面，而不是 `[data-theme='vscode']`。
   再加一套编辑器主题时，样式和组件一行都不用改。`applyTheme()` 顺手把 `data-chrome` 挂到
   `<html>` 上，只给两三处「非组件能表达」的规则用（滚动条宽度这类）。

2. **正文怎么分色，是标签而不是颜色。** CSS 看不见文字内容，而「这一段是对话」只能从文字判断，
   所以 `lib/code.ts` 过一遍正文 DOM，给元素贴上 `mn-code-line` / `mn-tok-string` /
   `mn-tok-comment` / `mn-tok-keyword` / `mn-tok-image`，颜色全在 CSS 里从 `--mn-code-*` 取。
   判断是有意的克制：标题和次要语言段（`data-mn-lang`）有明确标记，直接认；
   对话靠「引号里的部分占全段一半以上」——这样「他说：『走吧。』然后又说了很长一段」这类
   以叙述为主的句子不会被染成一句对话（实测过 0.5 这条线的四种情况）。
   数字单独包一层 span 上数字色。**不往正文里插任何原文没有的字**，唯一由我们生成的文本是
   图片的引用行（见下一条），因为它就是「这里有一张图」在这套排版里唯一诚实的写法。

3. **图一律不渲染，写成一行 `![](./路径)`。** 封面、卷首插图、正文插图都不例外——
   在编辑器形态里「打开一本书」应该是一片字，而不是一张全屏的图。占位行用的是图片在书里的
   原始路径（`OEBPS/Images/pic.png`），不是渲染时的 `blob:` 地址，所以 `useChapterHtml`
   要另外交出一张反向表（ObjectURL → 原始路径）给这里还原（见 hooks/useChapterHtml）。
   排版上还有两件必须做的事：`<figure>` 要拆开（图与图注本来就是两行，套在 figure 里会让
   「最深的块才是行」的判定把它们粘成一块，图也会落在行号列左边），以及让图注、表格这些
   原本小一号的地方在编辑器里回到 1em——行号列的宽度是按 `ch` 算的，字号一变窄，
   行号就整页对着不齐（见 决定记录 21）。

4. **预设是一次性的。** `preset` 在用户选中主题时和 `themeId` 一起写进阅读设置（等宽、不缩进、
   段间距 0、栏宽 56rem），之后用户怎么改都算用户的——它不是一层永远盖在设置上的覆盖。
   所以「选了编辑器主题，正文自动变成等宽」不需要在组件里写特例。

5. **首页是工作区，不是某一本书。** 编辑器形态下书架页默认不选中任何书，编辑区给一屏文字
   说明，等用户从左侧点一本书。之前的写法是「没选中就自动挑一本有进度的」，于是切到这套主题的
   那一刻，屏幕上直接是某本小说的正文——像被塞进了阅读器，而且没有明显的地方退回来。
   同理，阅读器里的左侧资源管理器列的是**整个书架**（不是只有当前这本）：
   「换一本书」和「回书架」都该在同一个地方，不用先退出阅读器再找。
   由此带出一个状态约定：侧栏展开的书 = 正在读的那本 + 用户另外打开的几本，
   当前这本永远展开（见决定记录 21 里为什么不能用「折叠集合」那种写法）。

编辑器那一套里几个刻意不做的东西：**假菜单栏**（文件/编辑/查看点了没反应，是纯骗人）、
**假窗口控件**（红黄绿灯或最小化/最大化，浏览器里点了不成立）、**假行号**（行号由 CSS counter
对着真实块级元素编号，和正文一一对应，不是画上去的）。做的是能用的那几个：活动栏切视图、
点已选中的图标收起侧栏（和编辑器一样）、`t` 开关侧栏、标签页记录这次会话开过的章、
缩略图点/拖可以跳、状态栏上的进度条与上下章（常驻，不用翻到章末找）、
以及书架页直接显示正文——没有封面那一层了。后来又多了一个：摸鱼模式把文件树和代码区压暗
（见决定记录 25）。

### 5.5 六套办公外壳：飞书 / 企业微信 / Word / Excel / PPT / 1688（2026-09-23 起）

编辑器形态证明了一件事：**用户要的不是「多几套配色」，而是「屏幕上就是那个软件」**。
顺着同一条路子，`chrome` 从两个值扩到八个，多出来的六个对应六套要假装的东西
（前五套 2026-09-23 做完，第六套 1688 客户工作台是 2026-09-24 加的，见决定记录 39）：

```
doc    飞书文档   一本书 = 一篇云文档，一章 = 文档里的大标题（大纲里逐个列出来）
chat   企业微信   一本书 = 一个会话，一段正文 = 一条消息（章 = 聊天记录里的一段）
page   Word      一本书 = 一份 .docx，一章 = 一页（导航窗格里逐个列出来）
sheet  Excel     一本书 = 一个 .xlsx，一章 = 一张工作表（底部标签切换）
slide  PPT       一本书 = 一份 .pptx，一章 = 一节（节里再切成若干张幻灯片）
desk   1688 客户工作台  一本书 = 一个买家会话，一段正文 = 一条消息
                        （右边那块客户档案里放这本书的档案与目录）
```

每一套都是亮暗两套主题，加起来 12 套；连编辑器那两套，内置主题从 8 套变成 20 套。

**`desk` 那一档是唯一一个「形状本身就带一块档案」的形态**：1688 工作台一屏里有四列
（功能栏 / 会话列表 / 聊天 / 客户档案），所以它比 `chat` 多一层右边那块面板。
换句话说：以后要做「拼多多商家工作台」「抖音小店客服」这类东西，形状落在 `desk` 这一档，
加一条主题数据就够了；要做「一个没有客户档案的聊天窗口」，那是 `chat`。

**形态名说的是形状，不是品牌。** 组件只认 `chrome`，不认主题 id——这条约束从 5.4 起就在，
现在它开始还债了：同一副 Word 外壳由「Word 亮」和「Word 暗」两套主题各自上色，
组件一行都不用改；以后想加「金山文档」或「腾讯文档」，只要形状落在 `doc` 这一档，
加一条主题数据就够了。`applyTheme()` 顺手把 `data-chrome` 挂到 `<html>` 上，
给两三处非组件能表达的规则用（滚动条宽度、纸张与幻灯片缩略图的尺寸常量——
它们要用的元素在正文容器**外面**，变量写在正文容器上取不到）。

**正文怎么切块只有一处。** 编辑器形态原先自己有一套遍历（`lib/code.ts`），
这次把它提成 `lib/blocks.ts`：编辑器的一行、表格的一行、聊天的一条、幻灯片的一张，
切法完全一样——「最里层的块级元素」，外加两件必须做的事（拆开 `<figure>`、
给落单的图包一层）。各形态只决定怎么摆放、怎么上色：`lib/chat.ts`（消息）、
`lib/sheet.ts`（行与单元格地址）、`lib/slide.ts`（按预算分张）都是**纯函数**，
所以外壳（编辑栏的当前行、幻灯片缩略图栏）和正文各算一遍也对得上，
不需要把派生数据在组件树里传来传去。

**功能区的处理方式是这一轮最花心思的地方**，规矩只有一句：**会响的按钮才可点，
灰着的按钮不许响**。

- Word 的功能区里，复制、字体、字号、行距、首行缩进、对齐、导航窗格、标尺、阅读视图、
  全屏、摸鱼模式都是真的——它们恰好就是这个阅读器本来就有的那几个设置，按下去字真的会变。
- Excel 的「冻结首行」是真的（表头粘在顶上）、工作表标签就是章、左下角那对箭头跳首末张、
  编辑栏与名称框跟着当前行走（`A57` 加那一行的原文）。
- PPT 用**幻灯片浏览视图**，不是编辑视图。编辑视图一次只显示一张，在浏览器里要自己造一套
  分页、还要和进度条打架；而浏览视图本来就是 PowerPoint 里正式的一种视图，
  一张张贴着排，正好用滚动的正文来表达。左侧那栏是节（= 章）+ 当前节的缩略图，
  缩略图和大图是**同一份内容**（同一个组件 + 一个缩放），不是另画一套占位图。
- 企业微信功能栏上那四个图标（消息 / 通讯录 / 日程 / 微盘）全是真的：换的是左边那一栏列什么
  （按最近阅读、按作者、按最后阅读日期、按文件）。聊天窗口底部**没有假输入框**：
  真聊天的输入框能打字，我们的不能，所以那个位置放的是这一章的位置（一条能拖的进度条，
  长得像输入框），右下角「发送」的位置是「下一章」——按下去真的翻章。
- 只读文档里本来就该灰的命令（粘贴、剪切、格式刷、字体颜色、加粗、查找替换、评论……）
  一律 `disabled`，`title` 里写明为什么（「只读」/「这个外壳里没有」）。
  一个按下去没反应的「发送」或「格式刷」，比少一个按钮更容易露馅。

**不编造数据。** 会话列表里的时间是这本书真实的最近阅读时间，头像里的字是书里作者的首字，
未读角标是还没读完的章数，Excel 里的「字数」「类型」两列是数出来 / 分类出来的，
Word 状态栏的「页面 3/12」就是第几章 / 共几章。唯一由我们生成的是各软件自己的结构性标签
（行号、页码、幻灯片序号、`Ln 171, Col 26`），它们说的是「这是第几段」，不是编出来的内容。

**图怎么放，每个形态不一样，而且是有意的。现在真的放图的只剩普通阅读器一处。**
表格的单元格装不下图，所以写成一行 `![](./OEBPS/Images/pic.png)`——和编辑器形态同一条
约定（见 5.4 第 3 条）。**飞书后来也归到「不显示图」那一类**（2026-09-24，决定记录 29）：
开一本书应该是一片字，一张全屏插页会把「这是一篇文档」冲掉。**企业微信最后一并归过来**
（决定记录 32）：一张封面在气泡里占掉大半屏，而那正是「这条消息是什么」最该说清的地方。
**Word（决定记录 35）与幻灯片（决定记录 38）先后归过来**：纸和版心的格子里虽然装得下
一整张插图，但一张封面铺满 A4 / 铺满 16:9 的版心，读起来也不像一份文档 / 一份演示文稿
——所以它们也写那一行引用。这不是「实现程度不同」，是这几屏用来放东西的地方本来
就不该由一张插图占掉。

**配色是抄的，不是调的**（同 5.4 的理由）。Office 三件套的中性色直接从 Fluent 2 的官方
token 表里取（Office 桌面版与网页版共用这一套：亮色 `#FFFFFF` / `#F5F5F5` / `#F0F0F0` /
`#E0E0E0` / `#242424` / `#616161`，深色 `#1F1F1F` / `#141414` / `#292929` / `#3D3D3D` /
`#D6D6D6` / `#ADADAD`），品牌色用 Office 三件套的官方色（`#185ABD` / `#107C41` / `#C43E1C`），
暗色版本是同一个色相抬到 60% 亮度。飞书用主蓝 `#3370FF` 与中性色
`#1F2329` / `#646A73` / `#8F959E` / `#F5F6F7`。企业微信一开始是按「微信系那副样子」
估的（深灰功能栏、白气泡、`#F5F5F5` 底），后来照桌面版截图重新量了一遍（决定记录 31）：
功能栏其实是淡蓝 `#DBE9F7`（选中那格 `#C9DEF7` / 墨色 `#267EF0`）、收到的气泡 `#E4E7EB`、
会话底 `#F5F7FA`、选中的会话行 `#3586F4`。
深色方向也不是把亮色反过来，而是照各家自己的深色模式来：飞书的文档页比外壳**略亮**，
Word 的页面是深灰的纸（不是白纸），PPT 连幻灯片一起压暗（不然暗色主题里会有一块刺眼的白板）。

**三条边界，和编辑器形态一致。**

1. **摸鱼模式**五套外壳都有效：它压的是正文那一片（`--mn-dim` + `.mn-veil` 的 `::after`），
   标题栏、功能区 / 工具条、状态栏不压。每套外壳自己决定哪一块算「正文那一片」。
2. **演示模式仍然只属于 VS Code 那两套**：它生成的是源代码，在 Word 里没有意义。
   按 Alt+Q 在办公外壳下什么都不改。
3. **阅读模式（上下滚动 / 左右翻页）在办公外壳里不适用**：它们的版面不是你自己的排版，
   是那个软件的（纸张、网格、幻灯片、消息流），分栏翻页在那儿不成立。
   ReaderView 里这条写成了一个条件（`paged = pageMode === 'paged' && (plain || code)`），
   设置面板里对应地换成一句说明，而不是留两个按了没反应的按钮。

**首页仍然是工作区，不是某一本书**（5.4 第 5 条的同一条）。五套外壳的首页都是它自己那一屏：
云文档首页、会话列表（有人在等你点）、Office 开始屏幕（新建 + 最近）。

飞书那一屏后来又单独重做过一次：用户给了一张真飞书云文档「主页」的截图，要求一比一复刻
（侧栏 300px、三张动作卡片、四个页签、一张五列的文档列表）。做法、量到的尺寸与「哪些是真的、
哪些灰着」的清单见决定记录 28。
README 里那张「书 ↔ 文件 ↔ 章」的对照表就是这一节这张映射表的用户版。

## 六、TXT：编码与分章

这一节是踩坑记录，因为这两件事的失败方式是「某本书正好没识别对」，最难靠肉眼发现。

### 6.1 编码检测的顺序是**先 UTF-16、再 UTF-8**

原本的顺序是 BOM → UTF-8 严格解码 → chardet → 兜底，验收脚本当场发现 UTF-16LE（无 BOM）被判成了 GB18030。

原因很隐蔽：**UTF-16LE 里的汉字是「低位字节 + 0x4E-0x9F」，而这些字节全都在合法 ASCII 范围内。**
`本` 是 U+672C → `2C 67` → 解成 `,g`；`书` 是 U+4E66 → `66 4E` → 解成 `fN`。
于是 UTF-16 的中文文本**能**通过 UTF-8 的严格解码，只是解出一堆看起来像正常 ASCII 的乱码，
`fatal: true` 这个本该救命的信号完全没响。

修法是加一个纯结构性的判据，而且排在 UTF-8 之前：

**判据一：换行的位置。** UTF-16 里换行是 `0A 00`（小端）或 `00 0A`（大端），
所以 `0x0A` 只会落在同一侧的字节位置上；而 UTF-8 文本里 `0x0A` 只来自换行，奇偶各半。
于是「`0x0A` 几乎全在偶数位」就是小端的强证据（阈值 0.05，且至少 8 个换行才判）。

这里有个中间版本的失败值得记下来：最初用的是「`0A` 后面是不是 `00`」的配对率。
实测比例只有 **0.71**，阈值定不下去——因为汉字 **「上」是 U+4E0A**，低位字节正好是 `0x0A`，
在正文里出现得极频繁，把配对率稀释了。改看**位置**（奇偶）就绕开了整个问题。

**判据二：高位字节大量为 0**，用于英文等 BMP 低码位的 UTF-16 文本。

最后还有一层 `looksLikeText()`（控制字符比例 < 2%）挡住「字节序猜反了」的情况。

### 6.2 自动检测不可能 100%，所以必须有手动覆盖

koodo-reader 的缺口也在这里：它用 chardet 看前 4096 字节，失败就退回 `"utf8"`，
而且**没有手动改编码的入口**（`charset` 字段存了但所有导入路径都传空值）。
短文件或者中英混排猜错时，用户没有任何办法。

我们的做法：检测结果 + 置信度 + 一句中文提醒写进书里，导入弹窗和「解析设置」都能改，
改完原地重新解析。自动检测永远会有例外，有个能改的入口比把猜测调得更花哨重要。

### 6.3 分章：逐级升级的模板 + 干扰项守卫

判定的是「这一行是不是标题」，而不是用一个正则切全文。模板逐级升级：

1. `第<数字>[章节節回话話集]` + 可选标题（数字支持中文/阿拉伯/全角）
2. `序章` / `楔子` / `引子` / `番外` / `尾声` / `后记` 这类固定篇名
3. `Chapter N` / `Part N`（英文小说）
4. 纯数字标题（`1.` / `十二、`）——**只在前三档命中少于 3 个时才启用**，这一档最容易把正文切碎

守卫条件（`isPlausibleTitle`）里最有效的两条是：长度 ≤ 40，以及**不含「。」**——
正文行几乎必然带句号，标题几乎不会。加上「不以逗号/分号结尾」兜住被截断的正文行。

验收样例里专门放了干扰项（`他翻到第一章的时候愣了一下，因为那一段被水浸过`、
`第 12 页上有一行批注`），断言它们必须留在正文里、不能变成标题。

**自动模式的探测是提前收工的**：扫到 3 个命中就认定这个规则可用，所以试三种规则几乎不花时间；
只有全都不命中时才会老实扫一遍（而且扫到 8MB 就停）。

### 6.4 卷/章层级

中文小说常见「第一卷 → 第一章」的两级结构。做法是：卷标题先不下结论，
**等下一行看是章节标题还是大段正文**——

- 后面跟的是章节标题 → 卷是目录分组，记成 `depth: 0` 的节点，那一行作为正文的居中标题并进首章；
- 卷标题之后攒了 ≥ 400 字还没出现章节标题 → 这个「卷」本身就是一章（有些网文就是卷里直接上正文）。

连续两个卷标题时，前一个卷的内容会被带上，不会丢字。

## 七、EPUB

### 7.1 章节归并：按目录目标切，不按 spine 切

很多 EPUB 把书切成几百个极小的 spine 文档（一个场景一个，甚至一段一个）。
按 spine 逐篇成章的话，目录里会出现 400 个「第 N 章」。

规则：**目录项落在哪个 spine 文档上，那里就是一个章节边界**；两个目录目标之间的连续文档合并进同一章。
目录项自带的层级当章节的缩进依据（压到 0-2 级），目录里没有链接的分组标题（nav 的 `<span>`、
ncx 的空 content）保留成 `groups` 里的卷节点。

验收样例刻意塞了一个不在目录里的 spine 文档，断言它必须并进上一章而不是自成章节。

### 7.2 净化分两层，而且不依赖单点

原计划只靠 DOMPurify。写 EPUB 验收时发现：**DOMPurify 在 happy-dom 下会静默什么都不做**——
不是配置问题，默认配置连 `<script>` 和 `javascript:` 都不处理。测试环境是这样，那真机环境会不会有
别的意外？把「正文不执行脚本」完全押在第三方库按预期工作上是没必要的风险。

于是改成两层：

1. **`scrubDocument()`**：我们自己删危险标签、`on*` 事件属性、危险协议。只依赖标准 DOM 接口，
   任何环境下的行为都一样。
2. **DOMPurify**：属性白名单、URL 校验、mXSS 这些深水区交给它。

验收脚本里加了一组恶意内容断言（script / iframe / object / onclick / `javascript:` 的 href 和 src），
现在在 happy-dom 下也是通过的——因为它验的是第一层。

### 7.3 「版式归我们，语义归书」

解析时剥掉书自带的一切样式：`<style>` / `<link>` / 全部 `class`，
内联 `style` 走白名单（只留 `text-align`、`font-style`、`font-weight`、`font-variant`、`text-decoration`），
带 `url()` 或尖括号的一律拒绝。

这是「一套主题管所有格式」能成立的前提。代价是**图文型 EPUB 的原始版式不保留**——
那需要一个单独的「保留原版式」开关，和统一主题是互斥的，留到以后单独设计。

### 7.4 图片与链接

- 图片：`src` 解析成 zip 内路径（处理 `../`、`%20`、大小写不匹配），重写成 `mnres://<path>`；
  远程图和 `data:` 原样保留；指向字体/音频之类（我们没抽出来的）则删掉属性，免得留一个坏请求。
- 跨章链接：解析成 `#mnref-<章号>:<锚点>`，由阅读器拦截后切章并滚到锚点——脚注就是这么工作的。
- **锚点 id 一律加 `mn-` 前缀，链接侧同前缀重写。** 不这么做的话，落点会在真实浏览器里
  被 DOMPurify 悄悄删掉：它默认开着 `SANITIZE_DOM`，凡是与 `document` / `form` 上的属性
  重名的 `id`、`name` 一律删（`target`、`action`、`method`、`name`、`title`、`length`…）。
  这些恰好都是书里常见的锚点名，而症状是「点脚注只切章、不滚到位置」。
  这个行为在 happy-dom 下不会发生（DOMPurify 在那里是空转的），所以验收脚本一开始看不见，
  现在由「正文里的锚点链接都有落点」这条端到端断言钉住。老式 `<a name="x">` 锚点也一并转成 id。
- 同章锚点：保留 `#fragment`，点击时在列布局里按 `offsetLeft` 换算出页码。

封面走回退链：`properties="cover-image"` → `<meta name="cover">` → `guide` 的 cover 页里的第一张图 → 文件名里带 cover 的图。
抽出来之后缩到 ≤400px 宽再存——书架上要显示的是缩略图，不是原图。

### 7.5 SVG 封面页与双语对照书（真实书验收补的两课）

**SVG 包 `image` 的整页图。** 日系 EPUB 的封面页爱写成
`<svg viewBox="…"><image xlink:href="cover.jpg"/></svg>`：SVG 的 `<image>` 认 `xlink:href` 不认
`src`，我们的资源重写够不着它——读者打开书第一页就是裂图；而且没有 CSS 尺寸约束的 SVG
会把多列版面撑爆。解析时把这类 svg 统一拆成普通 `<img>`（赶在 DOMPurify 之前转，
属性白名单怎么变都不影响），空壳装饰 svg 直接删。

**双语对照书。** 中日对照 EPUB（宝島社文庫这类）把次要语言的段落统一标成弱化样式
（`opacity: 0.4`）。这个样式原本在白名单过滤时被无差别剥掉，两种语言在阅读器里长得一模一样。
现在解析时把「opacity ≤ 0.7 的块级段落」识别为次要语言，标成 `data-mn-lang="alt"`，
阅读器据此提供「对照（次要语言降调显示）/ 只看译文 / 只看原文」三种模式
（`store/settings.ts` 的 `bilingual` → `--mn-alt-display` / `--mn-primary-display` / `--mn-alt-color`
三个变量）。没有这种标记的书完全不受影响。

**目录之前的 spine 文档。** 封面、彩插、版式说明通常在目录第一个目标之前，
而章节边界算法把 spine[0] 恒定为边界——它们会自成一个无标题的「第 1 节」。
现在这个前置组命名为「卷首」，当章处理（进度、目录都正常）。

## 八、阅读器：滚动与翻页

### 8.1 为什么不做 iframe

koodo-reader 用 iframe 装正文，代价是 CSS 变量过不去（主题要注入第二份）、划词定位和搜索都更麻烦。
我们用净化 + 作用域 CSS 拿到隔离：既然书的样式已经被剥光了，冲突风险本来就被消除了。
以后真遇到某本书的 HTML 作乱，再包一层 Shadow DOM 即可。

### 8.2 翻页用 CSS 多列，一屏放一列还是两列

列宽 = 一页宽度，`column-gap` = 两页之间的中缝，于是「一列 = 一页」，总页数 = `scrollWidth / 列宽`，
翻页就是给内容做一次 `translateX`。`column-fill: auto` 是关键：内容按顺序填满一列再排下一列，
缺了它浏览器会把内容平均分到所有列里，翻页顺序就乱了。

验收时确认了 `scrollWidth` 确实会算上列的溢出（列宽 672、中缝 37、6 列 → 实测 4217），这一点原本只是推测。

**一屏窗口（`.mn-frame--paged`）。** 多列内容不能直接放在留白的滚动容器里：
桌面宽窗口下正文栏宽远小于视口，`translateX` 之后上一页和下一页会同时露在两侧，
看起来就是「一屏三页、页页切半」。所以翻页模式多包一层宽度恰为「一屏」、`overflow: hidden`
的窗口，translateX 在窗口里滑。页面的垂直留白也移到窗口上——留白留在容器上会超出裁剪区，
同样会露边。

**一屏一列还是两列由可用宽度决定**（`ReaderView` 的 `measure()`）：两栏加中缝放得下就并排两页。
桌面宽窗口下只放一列的话，正文只是一条窄柱居中，两侧大片空白——那不叫左右翻页。
并排时一「页」（一次翻页的步长）是一屏两列，页码记的始终是「屏幕左边缘落在第几列」，
所以它一定是列数的整数倍。窄窗口放不下就退回单列，用户的栏宽设置仍然是每列的上限。

**窗口宽度必须是整数，中缝也不例外。** 多列布局的可见列数是
`floor((容器宽 + 中缝) ÷ (列宽 + 中缝))`，差一个像素就会少算一列——两页变一页、正文被拉成
一页宽。所以列宽和中缝都在 JS 里取整算好，再写成 `--mn-frame-width` / `--mn-col-gap`
两个变量（中缝交给 CSS `clamp()` 会有小数，整数除法立刻失守）。

**整页插图的两条规矩。** 多列没法切断一张图，图比一页高就会纵向溢出、把后面几页顶乱：
1. `measure()` 把列高写进 `--mn-page-height`，翻页模式下图片限高到它；
2. 图被缩到恰好一页高时，独占一段的图自带的 `margin` 会把它挤过页高，
   整图被推去下一列——当前页就成了空白页。所以翻页模式下独占段落的图
   （以及包着它的 `div` / `h1`）垂直边距一律归零，滚动模式保留。

### 8.3 测量为什么会失败，以及为什么要重试

翻页模式的所有几何都建立在「容器宽度」上，而这个值在你最需要它的时候可能是错的。踩过的两个坑：

**坑一：宽度为 0 时不能硬算。** 容器还没拿到宽度时，`clientWidth` 可能是元素自身的 padding（实测 32px）。
原来的代码有个 `Math.max(240, …)` 的下限兜底，于是页宽被兜成 240，正文被切成 16 列，
页数变成 16，`page` 被算到 15，`transform` 成了 `translateX(-3600px)`——而且因为没有尺寸变化，
`ResizeObserver` 不会再来纠正。现在的做法是**宽度不可信就这一拍什么都不做**，交给上层重试。

**坑二：一次测量不够。** 图片解码会改变列数（正文多出一列），字体就位也会。
修法是进入本章后反复测量，成功前每 250ms 试一次（最多 40 次），成功后每 200ms 再确认十几次然后收工。
**每次测量都以 `ratioRef` 为准**，所以重来只会收敛到正确位置，不会漂移。

### 8.3.1 「这一份 HTML 是不是本章的」也是一个前置条件

换章时新章的 HTML 要等图片资源就位才拿得到，期间 DOM 里还是上一章的内容。这时候量页、
算位置、恢复滚动位置全是拿旧内容算的，落点会先跳到别处再跳回来（症状：翻到上一章先闪一下
本章末尾）。所以 `useChapterHtml` 除了 HTML 还返回一个 key（这份 HTML 属于哪一章），
阅读器拿它和 `contentKey` 比对，**确认内容到位之后才开始量页和恢复位置**。
滚动的 scroll 事件同样要过这道闸：内容还是上一章时报出去的比例属于别的一章。

### 8.3.2 有锚点要跳的时候，恢复位置要让位

进章之后的 1.2 秒里有一圈「反复恢复位置」的重试（字体、图片晚一步就位时用）。它会一直
重写 `scrollTop`，所以脚注跳转刚落到锚点就会被下一拍顶掉——点脚注只切章、不滚位置。
现在这一圈恢复只在「没有待跳锚点」时跑，而且恢复的目标是进章时定下的那个固定值，
不会被中途的滚动事件带偏。

**这一圈重试也是「往下滚突然回弹」的成因。** 版面没变的时候重写同一个 `scrollTop`
一点用都没有，唯一的后果是把读者刚滚走的位置拽回来：进章时恢复点是章首（往下滚被弹回顶部），
往回翻时恢复点是章末（往上滚被弹回末尾）——报障里「每章开头往下滚、结尾往上滚会回弹」就是它。
两条规矩堵住：**版面没变就不重写**（拿上一次写进去的滚动范围当判据），
**读者一动就交还控制权**（wheel / touchstart / pointerdown / keydown 立刻停掉这一圈）。

### 8.4 `ratioRef` 是当前位置的唯一记录

这是验收时发现的真 bug：翻页只更新了 `page` 状态，没有更新 `ratioRef`。
于是翻完页再转屏（或改字号、改窗口大小）触发重新测量时，位置会跳回「进入本章时」的地方。

规则：**任何改变阅读位置的路径都必须同时更新 `ratioRef`**（翻页、跳锚点、拖进度条）。
少了这一行，症状是「翻了页，然后转一下手机，回到原位了」。

### 8.4.1 比例的方向要统一：是「已读列数」不是「列序号」

翻页模式存的比例是 `(已读列数) / 总列数`，也就是 `(屏首列序号 + 一屏列数) / 总列数`
（一屏一列时就是 `(页序号 + 1) / 总页数`；第 0 屏也有进度，和滚动模式的
`scrollTop / max` 一致：章末就是 1）。反解的时候要先减一得到「最后一列」，
再向下取整到整屏：`floor((round(ratio * total) - 1) / cols) * cols`。
少了这个减一，每次重新测量都会把位置往后顶一屏——连翻两屏、往回翻没反应，都是它；
少了整屏对齐，并排两页时位置会停在两页中间。另外测量改变了屏首列序号之后要把新比例
回报出去，否则库里存的还是旧位置，重新打开会差一屏。

### 8.5 进度持久化

- 滚动时进度每 100ms 上报一次（限流，不然进度条每帧都在 setState）；
- 写库是 1 秒防抖——滚动期间定时器一直被推迟，所以真正的写入发生在「停下来 1 秒之后」；
- 另外监听 `visibilitychange`(hidden) 和 `pagehide` 兜底，手机上切走 App 不会丢位置。

### 8.6 翻页模式下滚轮也翻页

滚动容器在翻页模式里是 `overflow: hidden`，不接管滚轮的话滚一下毫无反应，触控板的横向滑动
还会被浏览器当成「前进 / 后退」手势。所以窗口上挂一个**非 passive** 的 `wheel` 监听
（React 的 `onWheel` 是 passive 的，在里面 `preventDefault()` 不生效），规则：

- 位移累计到阈值才翻一屏，翻完锁 280ms——一次拨动的余量不该连翻好几屏；
- 两次事件间隔超过 200ms 算新手势，累计量清零（慢慢滚不会因为累计而突然翻页）；
- `deltaMode` 是「行」或「页」时换算成像素，不换算的话 Firefox 上一格滚轮只有 3 像素，永远到不了阈值；
- `Ctrl + 滚轮` 是缩放，让给浏览器。

一屏一列还是两列，翻页步长都取自排版测量出来的 `cols`，不在事件里另外判断。

## 九、PWA 与存储

- Workbox **只预缓存 app 外壳**（js / css / html / svg / png）。书一条都不进 precache——
  它在 IndexedDB 里，这本身就是离线能读的原因。`navigateFallback: index.html` 让任意路由离线都能打开。

  对一个「本地就是唯一副本」的应用来说这是灾难性的。设置面板里用 `estimate()` 显示占用。
- 开发时 `devOptions.enabled: false`：开着 SW 会让「改了没生效」变成常态。
- 图标从一张 `public/MioNovel.png` 由 `@vite-pwa/assets-generator` 生成全套（含 maskable 和 apple-touch）；
  界面里用的小图由 `bun run logo` 从同一张原图派生（第十节）。

## 十、界面与动效（2026-09-23）

这一轮把「能用」推到「看着像样」：补动效、去掉原生控件、给站点标识一套来源唯一的生成链。

### 10.1 动效的三个约束

**一、时长和缓动是 token，不是散在组件里的毫秒数。** `styles/app.css` 的 `:root` 里只有三档时长和
两条曲线：

```
--mn-dur-1: 130ms   跟着手指走的反馈（按下、悬停）
--mn-dur-2: 220ms   出现 / 消失
--mn-dur-3: 320ms   需要被看清过程的（面板、换页、逐个出现）
--mn-ease    cubic-bezier(0.32, 0.72, 0, 1)     主线，先快后慢
--mn-spring  cubic-bezier(0.34, 1.28, 0.64, 1)  只给开关、勾选这类小控件
```

三档之外不许现编。动画本身也只留四条实现（`mn-rise` 上浮淡入、`mn-pop` 缩放淡入、
`mn-fade` 纯淡入、`mn-skeleton` 高光扫过），加新效果先想能不能复用。
`mn-stagger` 用 `--mn-i` 把名单错开 22ms 一项——延迟必须封顶（书架封到第 11 项），
否则第 50 张卡要等一秒多才出现。

**二、颜色类属性有一条全局过渡。** `*` 上写了 `transition-property: color, background-color,
border-color, outline-color, fill, stroke, box-shadow`（130ms）。这一条同时解决三件事：换主题不再
「啪」地跳色、悬停换底色不再生硬、选中项高亮有过程。它只列颜色属性，位移和尺寸留给组件自己的
`transition-*` 工具类（工具类在 utilities 层，优先级更高，不会被这条覆盖）。

**三、动效必须能被系统关掉。** 一条 `@media (prefers-reduced-motion: reduce)` 把所有动画和过渡压到
1ms、把 View Transitions 的四个伪元素动画直接 `none`。注意这是**压时长，不是去掉样式**：最终状态
必须和开启动效时完全一样，否则关了动效就等于关掉功能。另外阅读器的平滑滚动是 JS 的
`scrollBy({behavior:'smooth'})`，CSS 管不着，所以那里单独读了一次 `matchMedia`。

### 10.2 为什么自己写 Select（以及 Dialog 为什么留着原生）

原生 `<select>` 的弹出列表由操作系统绘制：字体、圆角、阴影、动效一律改不动，暗色主题下还会突然
亮一下——整个界面里最显眼的「原生感」就是它。所以 `components/ui/Select.tsx` 自己实现了一个
listbox（portal + fixed 定位，跟着滚动重新定位而不是关掉），代价是多写一半无障碍代码：
`role=combobox/listbox/option`、`aria-activedescendant`、方向键/Home/End/Enter/Esc/Tab。

里面有一个跨组件的约定值得记：面板里的下拉开着时按 Esc，**只该关下拉，不该连面板一起关**。
面板的 Esc 监听在 window 的捕获阶段（它要先于阅读器的全局快捷键），所以下拉没法「抢先」处理。
做法是下拉打开时在自己的触发按钮上打一个 `data-mn-esc-local` 标记，面板看到事件目标落在带这个
标记的元素里就跳过——用一个属性把「谁先处理 Esc」讲清楚，比调整监听器顺序可靠。

`<dialog>` 反过来：焦点陷阱、Esc、backdrop 焦点隔离都是浏览器白送的，自己实现是凭空找 bug，
所以留着它，只把进出场动画补上（`allow-discrete` + `@starting-style`，不支持的浏览器直接显示）。

### 10.3 换页用 View Transitions，不做假动画

书架 ↔ 阅读器是两次整页切换，手写一套「旧页面淡出、新页面淡入」要么把两边都留在 DOM 里、
要么就是先切完再补一个入场动画（那看着就是两段）。改用 View Transitions API：
`App.tsx` 用 `react-router/dom` 的 `RouterProvider`（它比 `react-router` 那份多接一个
`ReactDOM.flushSync`），`navigate(path, { viewTransition: true })` 就能让浏览器把两侧各拍一张快照，
中间那段由 `::view-transition-old/new(root)` 的 keyframes 定义。不支持的浏览器直接瞬间切换——
没有垫片，也不值得垫。

### 10.4 标识与图标：一张原图，两条派生链

```
public/MioNovel.png（原图，352×367，187KB，唯一来源）
  ├─ bun run icons → favicon.ico / apple-touch-icon-180x180 /
  │                   pwa-64 / pwa-192 / pwa-512 / maskable-512   （安装用，带白底）
  └─ bun run logo  → logo-64 / logo-192（界面用，方形透明底）
                     + favicon.svg（内嵌 64px 位图的 SVG 外壳，页面用）
```

- 界面里用 `Logo` 组件，`srcSet` 只挂 64/192 两档：最大的显示尺寸是空书架上的 58px，192 够到 3x 屏。
- favicon.svg 不手写成 path：我们的标识本来就是一张位图，描一遍出来的不是同一个图形，还很难维护。
- **原图不进 PWA 预缓存**（`workbox.globIgnores`）。187KB 只服务图标生成，运行时用不到，
  让每次安装都下一遍不符合「离线可读」的成本账。
- 图标是**提交进仓库**的：clone 下来不装 `pwa-assets-generator` 也能构建。

### 10.5 验收时踩到的两个坑

**Tailwind v4 的位移/缩放不在 `transform` 里。** `translate-y-*` 写的是 `translate` 属性，
`scale-*` 写的是 `scale` 属性（`transform` 是 `none`）。用 `getComputedStyle(el).transform`
去验「悬停有没有抬起来」会永远读到 none——要读 `.translate` / `.scale`。
这不是 bug，但会让验收得出完全相反的结论。

**后台标签页的定时器会被节流。** 退出动画靠 `setTimeout` 收尾（见 `hooks/usePresence.ts`），
在不可见的标签页里这个 140ms 的定时器可能一秒后才跑。验收时读「浮层是不是已经卸载了」要留够
时间，否则会把「还没到点」误判成「没关掉」。

## 十一、验收方式

house 里没有测试框架也没有 CI（MioNote 就是 `tsc --noEmit` + 手动跑）。但解析器这块不行：
编码识别、分章、目录归并、路径重写的失败方式是「某本书正好没识别对」，靠手动找文件来测覆盖永远不够。

所以有一组验收脚本（每加一块「不看屏幕就发现不了」的逻辑就添一个，见决定记录 24 / 25）：

```bash
bun run samples     # 生成样例（含一个手写的、刻意很脏的 epub）
bun run verify      # 总入口：txt + epub + 演示模式 + 快捷键
```

- **`verify-parsers.ts`**（Bun 直跑）：UTF-8 / UTF-16LE / GB18030 / Big5 / 英文 / 无章节标记 /
  标题干扰项 / 手动编码覆盖 / 强制规则不被静默改写 / `charOffsets` 自洽。
- **`verify-epub.ts`**（happy-dom 顶一个最小 DOM）：元数据、章节归并、图片重写、样式剥除、
  ruby 保留、跨章与同章链接、卷节点、损坏文件的错误信息，以及一组恶意内容断言。

`make-samples.ts` 里那个最小 EPUB 是手写的（用 fflate 打包，连 PNG 都是自己编的），
里面刻意塞了真实书里会遇到的脏东西：章内 `<style>`、`class`、把图片撑到 9999px 的内联样式、
跨章脚注链接、不在目录里的凑数 spine 文档、ruby 注音。

之后每加一块「不看屏幕就发现不了」的逻辑，就再添一个脚本：`verify-decoy.ts`（八种语言的生成器，
见决定记录 24）、`verify-hotkey.ts`（快捷键的解析与匹配，见决定记录 25）、`verify-apps.ts`
（六套办公外壳的 token 完整性与正文形状：块切分、聊天消息、表格行、幻灯片、
客服工作台的指标与已读回执，见决定记录 26–27 与 39）。
`bun run verify` 是它们的总入口。

**GBK / Big5 的样例不由脚本生成**：Node 和 Bun 的编码支持里没有 GB18030 输出，
强行手写字节序列只会写出自己都不确定的文件。用 Windows 的 936 / 950 代码页转（命令在脚本输出里）。
Big5 那份是把简体正文塞进 950 代码页，Big5 里没有的字会被替换成 `?`——
所以对它的断言只覆盖结构（多字节解码成功、分章正确），不断言具体文字。

浏览器端做过一次完整的交互验收：拖入 TXT 和 EPUB → 书架出现卡片（封面、字数）→ 进入阅读器
（正文、ruby、图片从 blob URL 加载成功）→ 切换夜间主题（`data-theme` 变化带动正文、工具栏、
`<meta name="theme-color">` 一起变）→ 切到翻页模式（列宽 672、页数正确、翻页推进章节）→
刷新后阅读模式、主题、进度都恢复 → 目录抽屉列出卷节点和每章字数。

离线能力也实测过（生产构建 + `bun run preview`）：Service Worker 激活后
precache 里有全部 14 个外壳资源（index.html、两个 JS chunk——**包括按需加载的解析器 chunk**、
CSS、图标、manifest）。书在 IndexedDB 里，所以在没有网络时「打开 app → 打开一本已导入的书」
这条路径上没有任何东西依赖网络。

|---|---|---|
| 硬换行的英文 txt | 一行 = 一段，所以会变成一句一段 | 需要「合并软换行」选项：靠行长的聚簇程度和行尾标点比例判别，是个独立问题 |
| 整本塞进一个 spine 文档的 epub | 会变成一章 | 按文档内的 h1/h2 再切一次 |
| 图文型 epub 的原始版式 | 不保留（为了统一主题） | 单独的「保留原版式」开关，和主题互斥 |
| 大文件导入 | 主线程流式处理，靠分片让出事件循环 | 真出现卡顿就搬进 Worker |
| 全文搜索 | 没有 | 章节已按章存库，加 Worker 里线性扫描即可 |
| 办公外壳里的演示模式 | 只有 VS Code 那两套把正文换成源代码 | 每个形态要一份「那个软件的假文档」生成器（周报、预算表、演示稿），是独立的一块 |
| 主题 | 20 套内置（两套编辑器形态 + 六套办公外壳的亮暗）+ 自定义 CSS 逃生口 | 主题编辑器（往注册表写数据即可，UI 是独立工作） |

## 十三、不做的事

不做书签/标注（表已建好，因为不用 iframe 的渲染方式让 Range 定位很直接）、不做云同步与账号
（无后端是这个项目的定位）、不做划词翻译 / TTS、不做 PDF 与漫画。

## 十四、决定记录

### 17. 验收发现并修掉的问题（2026-09-22）

验收脚本和浏览器验收一共发现五个真问题，都记在上面相应章节里：

1. **UTF-16LE 被判成 GB18030** —— UTF-16 的中文能通过 UTF-8 的严格解码（六 6.1）。
2. **字符数把 HTML 标签也算进去了** —— 段数多的书百分比会偏（四 4.2）。
3. **卷目录项指错章** —— 收尾顺序让「前言」插在卷节点之前（六 6.4）。
4. **`<style>` / `<script>` 只靠 DOMPurify 挡** —— 它在某些 DOM 实现下是空转的（七 7.2）。
5. **翻页后 `ratioRef` 没更新** —— 重新测量时位置会跳回进本章时的地方（八 8.4）；
   以及连带的页宽测量失败没有重试（八 8.3）。

第 1、4、5 条都属于「不写验收就发现不了」的类型：功能看起来是好的，坏在边界上。
这也是为什么这个项目里有一个没有 CI 也要留的 `verify` 脚本。

### 18. 自己反复用一遍发现的问题（2026-09-23）

这一轮是「当成读者来用」：导入真书、翻页、跳脚注、改设置、切模式、刷新、缩窗口、拖键盘。
下面这些都不是猜的，是复现出来再修、修完再复现一遍确认的。

1. **刷新之后阅读设置全丢** —— 写 CSS 变量的 effect 只依赖 `settings`，首次渲染时容器还没挂载
   （书还在读），那一轮就白跑了，之后也不会再来第二次。症状是刷新后字号、栏宽、双语模式
   全部退回 CSS 默认值（八 8.3.1 旁的容器变量、五 5.3）。
2. **翻页连翻两页 / 往回翻没反应** —— ratio 反解差了 1 页，见 8.4.1。
3. **换章时位置先闪一下** —— 拿上一章的内容量页，见 8.3.1。
4. **脚注只切章、不滚到位置** —— 两个独立原因叠在一起：锚点 id 被 DOMPurify 按
   clobbering 删掉（七 7.4），以及恢复位置的重试循环把锚点位置顶掉（八 8.3.2）。
   前者只有真机才会出现，后者是两段代码抢同一个 `scrollTop`。
5. **重新解析完面板还显示旧数字** —— 面板存的是打开那一刻的书记录快照，改完不刷新，
   用户没法确认刚才那一下成没成（四 4.3）。
6. **二进制文件被当成小说收下** —— 书架多出一本乱码书，而且探测阶段失败连提示都没有（四 4.3）。
7. **翻页模式里「进度」和「看到的位置」会脱节** —— 测量改了页序号却不回报比例，
   重新打开差一页（八 8.4.1）。
8. **短章会被记成「已读完」** —— 滚动事件在版面还没就位时读到 `max = 0`，报了一个 1，
   恢复循环接着把位置顶到章末（八 8.3.2）。
9. **进阅读器后浏览器的滚动位置恢复会和我们的进度打架** —— 阅读器改为
   `history.scrollRestoration = 'manual'`，位置只由我们自己恢复。

顺带修掉的小问题：失败卡片上写的是「右键打开菜单」，而菜单其实是右上角的 ⋯；
「阅读模式 / 双语显示」两组按钮只有颜色区分选中项，补了 `aria-pressed`；
EPUB 之前没有重新解析的入口，解析器更新后只能删了重导，现在面板里也能刷一遍。

### 20. 编辑器形态（2026-09-23）

需求是「在工作的时候看，让老板以为我在编辑代码」：加一套 VS Code 主题，进去之后整个应用就是那个
编辑器——书架不再显示封面，直接把正文摆在编辑区里。做法与约束见 5.4，这里是这一轮踩到的：

- **配色是抄的，不是调的。** 深色取自 Dark Modern（编辑器 `#1F1F1F`、侧栏 `#181818`、
  焦点 `#0078D4`），语法色取自 Dark+ 的 token 表（对话 `#CE9178`、注释 `#6A9955`、
  关键字 `#569CD6`、数字 `#B5CEA8`）；浅色对应 Light Modern 与 Light+。
  测过：调过的颜色一眼就不是那个编辑器，而这套主题的全部价值就在「一眼是」。
- **行号不能用 `::before` 挤在行内。** 段落会换行成好几行，行号只该出现在第一行——
  用绝对定位把它放在块级元素的左侧内边距里（`padding-left: 计算值`），
  `display: grid` 那套在嵌套块（`<div><p>`）上会错位，float 又会和图片打架。
  编号用 CSS counter 对真实块级元素递增，所以**隐藏的双语段自动不占号**（display:none 不生成盒子）。
- **空行要当空行。** TXT 里的段落间隔段（`.mn-blank`）高度是按段间距算的，而编辑器形态下
  段间距是 0，行号会挤成一条线——改成 `height: 1lh`，空行就是一行高、照常编号。
- **状态栏上的 `max-lg:hidden` 一开始不生效**：`.mn-code__status-item` 自己写了 `display: flex`，
  和工具类同优先级、谁在后面谁赢。display 交回给工具类（`flex items-center`），
  CSS 只管尺寸和悬停——工具类和变体之间的先后关系不该由手写 CSS 的导入顺序决定。
- **缩略图的视窗框按「中心落在当前比例上」画**：滚动模式报的是顶边比例、翻页模式报的是已读列数
  比例，两种约定差半个框高。为一个装饰性的框去统一两种模式的语义不划算，取中间最省事的那条。
- 验收时发现 IAB 里 `el.scrollTop = x` **不派发滚动事件**（真实浏览器会），所以缩略图跳转后
  视窗框不跟手是环境现象；顺手把跳转改成自己直接写比例，不依赖那次事件，行为也更稳。

浏览器里实读过的路径：书架（资源管理器 + 正文预览、没有封面）→ 导入新书（自动选中并展开）
→ 点章节进阅读器 → 翻章（`←`/`→`、状态栏按钮）→ 搜索视图搜章节 → `t` 收起侧栏
→ 缩略图点击跳转 → 切到 VS Code 亮色 → 切回日间确认经典外壳与封面书架完全回来
→ 390px 宽（侧栏变浮层、缩略图隐藏、状态栏不溢出）。

### 21. 试读之后的三处返工（2026-09-23）

自己当读者用了一遍编辑器形态，报回来三个问题，都是设计上没想清楚，不是笔误：

1. **「为什么直接进入了我导入的小说」** —— 书架页原本有个兜底：没有选中就自动挑一本
   （优先有进度的），于是切到编辑器形态那一刻屏幕上是某本小说的正文。看着像被塞进了阅读器，
   而且**左侧资源管理器里没有任何地方能退回来**（它只列了当前这本）。
   改成：首页默认不选中（一屏文字说明，不摆图标），点书名才预览；面包屑的第一节
   「我的书架」点一下就回首页（和编辑器里点路径回上层一个意思）；菜单里也有「回到工作区首页」。
2. **「左侧菜单栏回不到书架」** —— 阅读器的资源管理器原来只传了 `books={[book]}`，
   整个书架是被藏起来的。改成一屏列出全部书：点别的书的章节直接换书（先把目标章写进它的进度），
   树底下加一行「回书架」。顺带修掉一个状态建模错误：原来用「当前这本 + 折叠集合」表达展开状态，
   结果**别的书永远展不开**（那个集合只能表达当前这本），改成「正在读的那本永远展开 +
   一个『另外打开的』集合」，当前这本不再进状态（见 5.4 第 5 条）。
3. **「有时候看不到上一章/下一章」** —— 那时候只有在阅读器里、并且翻到章末才有按钮
   （章末那对按钮是正文的一部分）。书架的预览里一个都没有。改成状态栏常驻：
   阅读器和书架预览的状态栏右侧都有「上一章 / 下一章」，走到头就置灰。

顺手处理的：图片一行 `![](./路径)`（5.4 第 3 条）带来的三个排版细节——
`<figure>` 拆开、孤立图片自己包一行、图注与表格在编辑器里回到 1em（行号列的 `ch` 宽度
跟着元素字号走，小一号的地方行号就整页错开 5px）；书详情面板在编辑器形态下也不再显示
封面缩略图（一个小方块破了「只有文字」这条约定，反而显眼）。普通形态的封面与缩略图
都做过回归确认没受影响。

### 22. 第二轮返工：演示模式、缩略图写真内容、树、加载闪一下（2026-09-23）

又当读者用了一遍，四个问题，都记在这里：

1. **缩略图画的是柱状条，不是内容。** 上一版按每段字数画一根横条——远看像进度条，
   不像文件。改成写真内容：3px 的等宽字排出来，长行按缩略图宽度折行（`Minimap.tsx` 里的
   `CHARS_PER_ROW` 和 CSS 里的 `font-size: 3px` 是一对常数，必须一起改）。
   这样缩略图的高度和正文高度成比例，视窗框的位置才有意义；长章节按步长抽稀，
   抽稀后文字被裁成细线——这是能接受的退化，不是画错。

2. **演示模式（Alt+Q）。** 用户要的是「领导来了」时一键把屏幕换成代码。
   做法是 `store/decoy.ts`（一个内存里的开关 + Alt+Q 监听）加 `lib/decoy.ts`
   （确定性的假代码生成器）。三条设计约束：
   - **只改显示，不改数据**：换的是渲染结果，书、进度、设置一个都不动，刷新即恢复。
   - **确定性**：同一段原文永远生成同一行假代码（种子取原文的哈希），
     否则重渲染时屏幕会自己变样，一眼就露馅。
   - **结构要像真文件**：开头两行 import，之后是「空行 → async 函数 → 成员语句 →
     错误处理 → return → `}`」的循环，括号成对、缩进对齐。生成器里刻意不出现
     「函数体里的 import」和「少一个右括号」这种懂行的人一眼能看出的假——
     这一层的全部价值就是别让人多看第二眼。
   入口有两个：Alt+Q（`useDecoyHotkey` 挂在 `App.tsx`，书架和阅读器都管用）和
   ☰ 菜单里的「演示模式（老板来了）」——菜单里那一项是为了让人知道有这个功能。
   演示模式只属于编辑器形态：普通形态下它什么也不改（第一版漏了这条，
   结果在普通形态里按过 Alt+Q 之后，章末的上下章按钮被一起吞掉了）。
   这一版后来被决定记录 23 整体重写成八种语言的完整源文件。

3. **左侧文件树的展开/收起坏了**，两处各有一个原因：
   - 书架页：点书名既切预览又展开，而「选中」这条逻辑会把它加回展开集合，
     于是**永远收不起来**。修法是让展开状态只归用户：选中逻辑不碰它，
     需要展开的场合（导入完成、搜索结果）显式调一次。
   - 阅读器：当前这本被写死成「永远展开」。改成换书时**一次性**展开新打开的那本
     （依赖书的 id，不依赖整条记录——记录会因为进度更新而换新对象，那样会把用户
     刚收起的那本反复打开），之后收不收听用户的。
   状态建模的教训写在代码注释里：一个字段只表达一件事，「展开」和「选中」
   混在一起迟早会互相顶掉。

4. **从书架点进章节会闪一下普通形态的加载页。** 编辑器形态下那三种状态
   （书还没读出来 / 读不出来 / 没能解析）走的是普通形态的整屏 `Screen`——
   带标识、写着「正在打开…」。骨架和真窗口不一样，看着就是「加载了一下」。
   现在这三种状态在编辑器形态下都渲染 `CodeFrame`：一个空的编辑器窗口
   （同样的标题栏高度、活动栏宽度、状态栏），不摆标识、不转圈、不写「正在打开」。
   用 MutationObserver 逐帧验过：从书架点进阅读器之后，第一帧起就是编辑器外壳，
   全程没有出现过标识。

状态栏右下角现在是「本章字数 / 全书字数」（`3011 字 / 2.7 万字`），
滚动模式下预览里读的那一段也会按同样的节奏写进进度。

### 23. 演示模式做成八种语言（2026-09-23）

第一版的演示模式是「把中文换成随机英文单词」，用户看了一眼就说太假。换成**按语言生成完整的源文件**：
`lib/decoy.ts` 里每种语言给一份模板（文件头、代码块、收尾、单行填充），正文的每一段对应文件里的一行。

- **结构决定可信度。** 现在生成的是：Java 的 `package` + `@Service`/`@Mapper` 注解 +
  `public class X` + 若干 `@Transactional` 方法；C# 的 `using` + `namespace` + 主构造函数注入；
  Python 的 `from __future__` + 类 + `def` + 类型标注；C++ 的 `#include` + `namespace example` +
  成员函数定义；React 的 hooks + JSX；Vue 的 `<script setup>` + `<template>`；
  Go 的 `package` + struct + `func (s *X) ... error`；Rust 的 `use` + `derive` + `impl`。
- **三处名字必须同源。** 文件名、文件里的类名/组件名、标签页标题都从 `makeCtx(preset, seed)` 推出来，
  seed 统一由 `decoySeed(bookId, chapterIndex)` 给。踩过的坑：第一版是「目录树按章节标题哈希、
  正文按正文内容哈希」，结果 `ReportMapper.java` 里写着 `class CatalogService`。
- **不生成半截函数。** 块放不下时不是截断，而是用**单行内容**（常量声明 + 一句注释）填满剩下的位置——
  截断会留下「声明了变量却没有返回值」的函数，那在 Go / Rust 里是编译错误。
  另外方法名用「动作 + 字段」交叉（`createSku` / `updateQuantity`），只有八个动作词的话
  长章节里会出现两个同名方法，那在 Java / C# 里是编译错误。
- **开关持久化。** 阅读设置里能手动开、能选语言，那它就该像别的设置一样被记住
  （`mionovel:decoy`）；Alt+Q 改的是同一个开关。上一条决定记录里「不持久化」的理由
  （怕用户以为书丢了）让位给了「设置面板里能改的东西不该刷新就忘」。
- **标签栏也要换。** 连浏览器标签页的标题和图标一起换：小说图标配代码窗口，
  是老板扫一眼标签栏就能发现的破绽。标题走 `useDocumentTitle`（CodeShell / CodeFrame），
  图标走 `useDecoyFavicon`（语言色的 SVG 小方块，data URL，不加资源文件）。

### 24. 演示模式返工：交给 highlight.js，生成「任何长度都合法」的文件（2026-09-23）

用户看了生成的 Java 之后说「缩进呢？highlights 呢？这明显是假的」，并且直接点出
「不是有 highlight.js 吗」。三条都成立，这一轮按这三条重做：

1. **缩进看不见是 CSS 的事，不是生成的事。** 生成的文本里一直有那四个空格，
   但 HTML 默认把行首连续空白折成一个空格——屏幕上代码平铺到左边，一眼假。
   修法是在演示模式下给正文加 `.mn-content--code`，`white-space: pre-wrap`
   保留空白、超长行仍然折行（编辑器的 word wrap）。
   教训：**「文本里有」和「屏幕上看得见」是两件事**，验收要读屏幕，不能只读数据。

2. **上色交给 highlight.js。** 之前自己维护一套 tone（关键字/字符串/类型/函数…）
   贴在生成的行上，结果是「关键词有色、其余全灰」——因为真实语法高亮的色彩分布
   远比我手写的复杂（类型、函数名、参数、属性、注解各一色）。现在生成器只输出
   **纯文本**，`lib/highlight.ts` 逐行 tokenize，`hljs-*` 类名在 `styles/code.css` 里
   映射到主题变量——色彩回到主题那一份，换主题时高亮跟着变。
   逐行 tokenize 是刻意的：正文一行 = 文件一行 = 缩略图一条，跨行 split 会切断 span；
   而生成的文件里没有跨行结构（没有块注释、没有多行字符串），所以逐行是准确的。
   按需加载：highlight.js 只在演示模式被 `import()`。

3. **任何长度的章节都要生成合法的文件。** 这是最难的一条，也是「一眼假」里最扎眼的：
   之前段落少的时候会把文件头切一半，屏幕上出现没有收尾的 `class X {`、孤零零的 `@Mapper`，
   或者半截构造函数（`pub fn new(...) -> Self {` 紧跟一个 `}`）。现在按「组」组装：
   `preamble` / `open` / `fields` 都是**要么整段写、要么整段不写**，容器放不下就退化成
   只有顶层声明的文件（`package x;` 加空行本身就是合法 Java）。块放不下时不截断，
   改用单行常量填满尾部。方法名用「动作 × 字段 × 变体」交叉 + 去重序号，
   保证不会出现两个同名方法（Java / C# 里是编译错误）。

配套加了一个验收脚本 `bun run verify:decoy`：八种语言 × 1..80 行 = 640 份文件，
逐份检查「空块、括号配对、结尾悬空、方法名重复、行数不符、缩进丢失」——
它抓到的第一版问题就有 156 个（全部是上面第 3 条那类）。这类脚本和解析器的
`verify` 是一回事：**生成器的 bug 不看屏幕发现不了，那就让脚本逐份读**。

### 25. 摸鱼模式与可自定义快捷键（2026-09-23）

这一轮加的是「让领导看不出来」的另一半。演示模式（决定记录 22-24）改的是**显示什么**——
小说变成源代码；这一轮的两件事改的是**有多亮**和**怎么按**。

**一、摸鱼模式：压暗的是正文区，不是整个窗口。** `store/dim.ts` 存开关与程度（0-1），
`--mn-dim` 写在 `.mn-code` 根上，左侧文件树与右侧代码区各自用 `::after` 盖一层黑纱
（`styles/code.css`）。三条理由：

- **标题栏、活动栏、状态栏不压暗。** 隔着几步看过去，亮的边框围着一块暗的内容区正是
  「开着编辑器」的样子；整窗压暗会变成「屏幕关了」或「人不在」，那不是这个功能要的观感。
- **用一层叠上去的黑纱，不是 `filter: brightness()`，也不改正文颜色。** 它能顺手调，
  而且正文那套颜色（主题 token + 语法高亮）一个字都不用动——`filter` 会让「暗」这件事
  渗进每一处颜色计算，以后调主题时到处是它的影子。
- **`::after` 而不是塞一个真元素。** 它纯装饰：不必进 DOM，也不必进无障碍树；
  两块正文区自己盖自己的，侧栏在窄屏变成浮层时黑纱跟着它走，不需要一个「活动栏有多宽」的常数。

开关与程度**持久化**（`mionovel:dim`），理由和演示模式一样：设置面板里能改的东西，
不该刷新一下就忘。它和演示模式是两个独立开关——一个换内容、一个改亮度，
组合起来是「一份暗着的源代码」，谁也不用知道对方存在。

**二、快捷键可自定义：只有一处监听、一种表示法。** `store/hotkeys.ts` 存两个功能各自的
组合串（`Alt+Q` / `Alt+S`），`hooks/useGlobalHotkeys.ts` 是唯一的 window 监听，
判定在 `lib/hotkey.ts`：

- **组合存成给人看的一行字**（`Alt+Q`）。菜单提示、设置里显示的都是它，
  存成 `{ctrl, alt, code}` 那种结构只会多一层翻译，而它本来就要显示给用户看。
- **按 `event.code`（物理键位）判，不按 `event.key`。** Alt 按住时 `key` 会跟着键盘布局走
  （德语布局里 Alt+S 打出的是 ß），只有 code 说的是「你按了哪个键」。旧实现里
  `code !== 'KeyQ' && key !== 'q'` 那种两头兜的写法，在可自定义之后没法维护。
- **必须带一个「真」修饰键（Ctrl / Alt / ⌘）。** 全局快捷键不管焦点在哪都会响，
  只带 Shift 的话，在搜索框里打一个大写字母就会把屏幕压暗。录键时挡下并给出理由。
- **录键那一下必须被吃掉。** 用户想把 Alt+S 绑给演示模式，如果那一下同时被全局监听看到，
  摸鱼模式会先切一遍。两道保险：控件本身 capture + `preventDefault` + `stopPropagation`，
  以及 store 里的 `recording` 标记（全局监听看到它就整个让位）。第二道不是多余的——
  事件直接派发到 window 时，capture 与 bubble 在同一节点上都会跑，`stopPropagation`
  拦不住同节点的监听。Esc 取消录键走的是既有的 `data-mn-esc-local` 约定（第十节 10.2），
  不然一下 Esc 会把设置面板一起关掉。
- **两个功能不能绑同一个组合**，录的时候直接挡住（谁先响应说不清），错误文案里点名是哪一个。
- **摸鱼模式的键只在编辑器形态下响应**，判断读 `<html>` 上的 `data-chrome` 而不是
  `useChrome()`：阅读器里某本书可能开着独立主题，那一层才是此刻真正生效的形态。
  演示模式的键保持原样（哪儿都能按，但只在编辑器形态里有可见效果）。

**三、验收发现的两件事。** 一条是真 bug：`parseCombo` 要求「至少两段」，
于是只按一个字母时报的是「这个组合认不出来」而不是「要带上 Ctrl 或 Alt」——
文案对不上原因，用户不知道该按什么。现在解析只管结构（`K` 是能解析的），
「缺修饰键」由 `comboProblem` 单独判。另一条是环境现象：`getComputedStyle(el, '::after').opacity`
在 IAB 里会读到过渡中的旧值（几十毫秒到一秒不等），量黑纱要看 `--mn-dim` 本身，
或者等过渡结束再读；截图和最终计算值都是对的。

**四、快捷键的验收脚本。** 这段逻辑的失败方式是「某组键按下去没反应」或者更糟——
「按下去触发了别的功能」，两种都不看屏幕发现不了。`bun run verify:hotkey` 把判定
拉出来逐条断言（28 项）：修饰键任意顺序的解析、`KeyQ`/`Digit1`/`F2`/`Slash` 的来回换算、
多按一个修饰键不算命中、德语布局下 Alt+S 仍要命中、单字母与只带 Shift 要被挡下。

浏览器里实读过的路径：切 VS Code 暗 → 阅读设置里出现「摸鱼模式」一栏 → 开关打开（两块正文区
压暗、边框仍是亮的）→ 拖程度滑条 → 点录键改绑（Esc 取消、按 Alt+Q 被冲突挡下、Backspace 恢复默认）
→ ☰ 菜单里的提示跟着新键位变 → 旧键位失效、新键位生效 → 刷新后主题 / 压暗 / 演示模式 / 键位都还在
→ 切回日间主题：那一栏消失、按 Alt+S 也不改任何状态 → 阅读器里 `t` 收起侧栏照旧。

### 26. 五套办公外壳（2026-09-23）

需求是「按着做 VS Code 主题的经验和方法，做飞书、企业微信、Word、Excel、PPT，都要亮暗两套」。
一句话就是这一轮的全部：**同一个做法重复五次**——形态写进主题、组件只认 chrome、
颜色抄官方的、外加一层只有那块屏幕才需要的正文形状。做法与约束见五 5.5，这里是这一轮踩到的。

**一、颜色去哪儿抄。** VS Code 那两套能抄 Dark Modern 与 Light+ 的 token 表，
Office 三件套也有一份公开的：Fluent 2 的 `@fluentui/tokens`（`npm i @fluentui/tokens` 就能读到
`generateColorTokens()`，亮暗两套，Office 网页版用的就是它）。所以 Word / Excel / PPT 的中性色
不是估的，是把 token 值一个个填进去；品牌色用 Office 三件套的官方色（`#185ABD` / `#107C41` /
`#C43E1C`），暗色版本用同一个色相抬到 60% 亮度算出来（一个小脚本算的，不是手调的）。
飞书与企业微信没有公开的 token 包：飞书用它的主蓝 `#3370FF` 与那套中性色，
企业微信的强调色从它官网 CSS 里取到的主蓝 `#0082EF`，聊天那副样子按微信系来
（深灰功能栏、白气泡、`#F5F5F5` 底）。**深色不是把亮色反过来**：飞书的文档页比外壳略亮、
Word 的页面是深灰的纸、PPT 连幻灯片一起压暗——这三条都是照各家自己的深色模式定的。

**二、把编辑器的遍历提成公共块模型，是本轮最值的一次重构。** `lib/code.ts` 里那套
「最里层的块级元素才是行」+ 分类器（对话/标题/注释/图片）+ 图片整理，四种新形态全都需要。
提成 `lib/blocks.ts` 之后，五个形态共享同一份切分，各形态只剩「怎么摆」。
代价是 `lib/code.ts` 要动刀——它已经跑了两个版本、有 `verify:decoy` 兜着，
改完在浏览器里把编辑器形态（行号、语法色、缩略图、演示模式）重新读了一遍确认没回归。

**三、五个只有真上手才会发现的问题**，都记在这里：

1. **双语的 `--mn-alt-display` 会把表格和聊天拆散。** 那两个变量给的值是 `block` / `none`，
   而表格的行、聊天的消息行自己就是网格/弹性容器——把它们设成 `block` 之后，
   四列摊成一行文字、头像和气泡上下叠起来（屏幕上看就是「表格散架了」）。
   隐藏是同一件事，显示不是：所以补了 `--mn-alt-row` / `--mn-primary-row`，值是 `none` 或
   「它自己的布局」，CSS 里两套形态各自取那一对。
2. **`<figure>` 里的图会被整块丢掉。** `figure` 不在块级选择器里，而图又不是块——
   于是「图注在、图没了」（在聊天里就是一条空消息、在幻灯片上就是一张空白）。
   修法是把 `normalizeMediaLines` 从「编辑器的图片整理」升格成块模型的一部分：
   拆 figure、给落单的图包一层，两种媒体模式（引用 / 原图）都要做。
3. **外壳的 CSS 挂错了根类。** Word / Excel / PPT 的正文样式原本写在 `.mn-word` / `.mn-excel` /
   `.mn-ppt` 下面，而这三个类根本不存在（根是 `.mn-office`，正文容器是 `.mn-word__body`）——
   结果是**一条规则都没生效**，屏幕上看到的是普通形态那套排版。这类错误不看屏幕发现不了：
   DOM 数据、颜色、行数全是对的，只有版式不对。修完顺手把纸张宽度与缩略图尺寸这两个
   常量挂到 `html[data-chrome='page'|'slide']` 上——标尺和缩略图在正文容器**外面**，
   写在正文容器上的变量它们取不到（宽度会退成 auto：标尺横贯全窗、缩略图撑满一栏）。
4. **编辑栏和表格各行其是。** 表格里的「当前行」按章内比例算，编辑栏原本按全书比例算——
   翻到第 3 章时两边差着两章的位置（A4 对着一行里第 5 段）。这是「同一个量有两个来源」的老问题，
   修法是给外壳加一个 `chapterPercent`（章内比例），和正文用同一个。
5. **空行与重复的章标题到处都是。** TXT 的段落间隔段（`<p class="mn-blank">`）在聊天里变成
   一个个空气泡、在表格里变成一行行空白；而每章开头那个章标题又和大纲/标题页/分隔线上的
   同一句话重复一遍。三处各自过滤（只丢「开头 + 是标题 + 文字相同」的那一个，
   正文中间的小标题照旧当分隔线和标题用）。

**四、验收脚本按新脚本的规矩来。** `bun run verify:apps`（75 项）分两段：主题注册表那一段
（每套 18 个 token 一个不缺、声明了 code / chat 的把那一层也补全、每个形态都有亮有暗、
自带的排版参数在范围内、生成的样式表里有每一段）和正文形状那一段。最能说明问题的是幻灯片：
「一段文字被搬进标题、正文还是丢了」，盯着屏幕看不出来，但**每一段恰好出现一次**（带重数的
多重集相等）是可以逐份断言的——3 / 8 / 20 段三种长度各跑一遍。这和 `verify:decoy` 的
「行数要对齐」是同一路数。

**五、浏览器里实读过的路径。** 五套外壳 × 亮暗共 10 套，逐套走一遍：切主题 →
看首页（云文档列表 / 会话列表 / 开始屏幕）→ 打开一本书 → 看正文版式（纸张宽度、标尺、
页边距标记、网格的行列、幻灯片缩略图、气泡与头像）→ 换章（大纲 / 工作表标签 / 节 /
聊天记录）→ 状态栏与编辑栏跟着走 → 摸鱼模式压暗的是正文那一片 → 切回普通主题确认
经典外壳与封面书架完好。另外单独读过的：编辑器形态（行号、缩略图、演示模式）没被这一轮
重构弄坏；EPUB 的图在聊天里是一条图片消息、在幻灯片上是一张图、在表格里是一行引用；
390px 窄屏下会话列表变成浮层（不然功能栏 46 + 列表 200 只剩 144 给消息，那不是聊天窗口，
是一条竖着的缝）。

### 27. 办公外壳里的「真」与「假」：一条线怎么划（2026-09-23）

做这五套外壳时反复撞上同一个问题：**哪些东西可以只是看起来像，哪些必须真能用？**
照编辑器的经验（5.4 那三条不做：假菜单栏、假窗口控件、假行号），这一轮把它写成一条可执行的线：

- **会响的控件必须真响。** 功能区和工具条上凡是能按的（不是灰的），按下去屏幕就得变。
  Word 的复制 / 字体 / 字号 / 行距 / 缩进 / 对齐 / 导航窗格 / 标尺 / 阅读视图 / 全屏、
  Excel 的冻结首行 / 工作表标签 / 章节箭头、PPT 的备注 / 节栏、飞书的字体字号对齐行距缩进、
  企业微信功能栏那四个视图——全部有真实行为。它们恰好都是这个阅读器本来就有的设置，
  所以「真」不需要额外造一套功能，只需要把它们摆到那个软件该在的位置上。
- **本来该灰的就灰着，并且说清为什么。** 只读文档里粘贴/格式刷/字体颜色/加粗/查找替换
  本来就是灰的，我们照做（`disabled` + `title`），这比让它们「装作能用」诚实，也更像。
- **占位的空间可以留，但别做假动作。** 功能区里那些灰命令的图标照画（那一格本来就该有东西），
  但**不画**假菜单栏、假窗口控件、假滚动条。
- **数据一律真。** 文件名、时间、字数、进度、未读角标、作者、工作表里的类型列——都是本地的
  真值或算出来的值。唯一的例外是各软件自己的结构性计数器（行号、页码、幻灯片序号、
  `Ln 171, Col 26`）：它们不声称是内容，只声称「这是第几段」。
- **两个「不能真」的地方，改成真的别的。** 聊天窗口的输入框在浏览器里发不出消息，
  所以那个位置放的是**这一章的进度条**（长得像输入框，拖得动），右下角「发送」的位置是
  「下一章」——按下去真的翻章。不摆一个打了字没反应的框。
- **单击就是打开。** Office 的开始屏幕在真软件里是「先选中、再双击」，但我们这副界面里
  没有别的选中态，一个只选中不打开的列表看着更像坏了，所以单击直接打开、行尾的 ⋯ 进解析设置。

这条线的意义和 5.4 那条一样：**这套外壳的全部价值就是别让人多看第二眼**。
一个按下去没反应的按钮、一行编造出来的时间、一个发不出消息的输入框，都是会让人看第二眼的东西。

### 28. 飞书云文档首页按截图一比一复刻（2026-09-24）

需求是「飞书主题按这张图改造，一比一复刻」——图是真飞书云文档（个人版）的「主页」：
左边一条 300px 的空间栏，右边是三张动作卡片、一条页签和一张五列的文档列表。
上一版的云文档首页只是「像个云文档列表」，这一版是把那一屏量下来重画的。

**一、先量再画。** 拿到的是一张 1920×914 的截图，所以尺寸不是估的，是从像素里读出来的
（做法记在这一节末尾）：侧栏 300（底色 `--mn-bg`，正文区 `--mn-surface`）、品牌行 52 高、
搜索框 32 高圆角 8、导航行 36 高间隔 2、行内文档图标 20、卡片 294×64 间隔 20、
卡片到页签 17、页签行 48、表头 36（下边线正好落在 y=234）、列表行 56、
四列数据各 224 加行尾 34 的 ⋯、内容区左起 30 右到 18（再减去 8px 的细滚动条）。
这些数写进 `styles/doc.css` 的注释里，改一个要连着看相邻的几个。

**二、颜色全部走 token，只有两处例外。** 量到的色号和现有 token 几乎一一对上：
侧栏 `#F5F6F7` 就是 `--mn-bg`，卡片边框 `#DEE0E3` 就是 `--mn-border`，
选中态那颗 `#D3DEF6` 是强调色 15% 铺在侧栏底色上（所以写成
`color-mix(in srgb, var(--mn-accent) 15%, transparent)`，不写死色号）。
两个例外都是**产品记号**：`IconFeishuMark` 那三个色（`#3370FF` / `#133C9A` / `#00D6B9`）
和三张卡片上的彩色插图（新建的蓝页、上传的橙云、模板库那三个形状）——它们是插图不是控件，
跟着主题变色就不像那个产品了，和 `public/MioNovel.png` 是同一个道理（文件头里写明了）。
另外实心色块上的白线也写死 `#fff`：那是记号自己的墨色；徽标外圈那道「挖空」例外，
它露出来的必须是卡片底色，所以取 `var(--mn-surface)`（用 `style` 写，presentation
attribute 里的 `var()` 不保证被解析）。

**三、哪些是真的，哪些灰着。** 这一屏上可点的东西只有四个来源：导入、打开、阅读设置、
视图与列设置。它们被摆在真飞书放它们的位置上——三张卡片里的「新建」「上传」（都是导入，
真飞书建空白文档和上传本地文件也是两条路通到一个结果）、「我的文档库」右边那个加号（导入）、
行尾的 ⋯（解析设置与删除）、头像一个菜单（阅读设置 / 导入 / 全屏）、
「我的文档库」右边第二个图标（阅读设置）、页签（最近访问 / 归我所有）、
筛选（全部 / 在读 / 未读 / 已读完）、显示设置（四列的显示开关）、视图切换（列表 / 网格）、
卡片下面那个搜索框（过滤列表，顶栏的放大镜把光标送进去）。
其余的一律 `disabled` + `title` 写清为什么：云盘、知识库、智能纪要、新建或置顶知识库、
模板库、新建视图、顶栏三个图标、底部三个（打印 / 工具箱 / 回收站）。
**「与我共享」和「收藏」两个页签老实空着**——本地文件不上传，「共享」无从谈起，收藏也是
这个应用没有的功能，所以它们各自给一句说明，而不是把同一批书换个标题再列一遍。
同样老实的是「所有者」和「位置」两列：TXT 解析出来的书没有作者，就写「我」；
文档都在一个空间里，就写「我的空间」。宁可是一列一样的真话，也不要三个编出来的同事
（决定记录 27 那条「不编造数据」）。

**四、四个页签、一个筛选、一个箭头，落到数据上就是两个纯函数。** 这类判断不看屏幕发现不了
（排错了、筛丢了，扫一眼列表未必看得出来），所以照老规矩放进 `lib/appdocs.ts`：
`readStateOf`（按全书百分比分在读 / 未读 / 已读完，和阅读器、状态栏同一个数）和
`homeRows`（页签 + 筛选 + 排序）。`verify:apps` 加了 21 项断言，包括那一列时间的写法
（今天 / 昨天 / 今年 / 跨年，`docTimeText` 的 `now` 参数就是为断言留的）和
「时间一样时按书名兜底」这种排序稳定性。

**五、三个只有真上手才发现的问题。**

1. **下拉菜单需要勾选位，触发器不一定是 ⋯。** 「筛选」「显示设置」要在菜单里显示当前选中项，
   而首页上那两个入口是一段带图标的字、头像那个入口是一个圆头像。所以 `AppMenu` 加了两样：
   `AppMenuItem.checked`（左边留一个勾选位，没勾也占着宽度，菜单不会跳）和 `trigger`
   （不传还是那个 ⋯；传了就只包一层，长相交给里面的东西）。这两样是给所有外壳共用的，
   不是给飞书开的后门。
2. **列宽是 JS 算出来的，窄屏收列也得由 JS 决定。** 显示设置改的是 `grid-template-columns`，
   它是 inline 样式；CSS 那边用媒体查询覆盖它会让格子数和单元格数对不上，多出来的格子会掉到
   下一行。所以窄屏时不是「CSS 把这一列藏起来」，而是 `useNarrow()` 读 matchMedia，
   由 JS 从 template 里去掉那一路（1180px 以下去掉所有者与创建时间，960px 以下再去掉位置）。
3. **卡片图标是插图，墨迹只占 24 格里的 16–18 格，按 24 格画会小一圈。**
   同一个 30px 的盒子里，界面图标（描边、画满）看着正好，插图（云、三角、折角纸）看着小一号。
   修法是量出来再定尺寸：`getBBox()` 在浏览器里把每个记号的墨迹框读出来（那次读到新建
   16.4×18.2、上传 17.6×16.9、模板 16.6×15.6、商标 19×16.5），按「墨迹要占满视觉大小」
   反推盒子——卡片图标给到 40px（再往左拉 6px 把位置对回卡片内边距上），商标 25×24。
   这条对以后再画插图类图标同样适用：**描边图标画满格子是对的，插图要按墨迹定尺寸。**

**六、怎么从截图上量尺寸**（这套办法以后复刻别的界面还能用）：`sharp` 读原始像素
（`node_modules` 里就有，不必装新的东西），按行/列做「非背景色」的游程统计，
量出所有横线、竖线、文字块的起止；再抽几个点的真实色值当配色依据；
看不清的小图标就裁下来放大 8-16 倍看。文字的位置量的是**墨迹**，所以比边框位置窄 2-4px
（字体自带的侧边距），对位时两个都要看。

**七、浏览器里实读过的路径**：飞书亮 / 暗两套都看了整屏；四个页签来回点（与我共享、收藏
各自给出说明，最近访问 14 行）；筛选点「已读完」→「没有已读完的文档」，再点回「全部文档」；
显示设置关掉「所有者」→ 表头少一列、grid 从五路变四路，再打开；视图切到网格（14 张卡）
再切回列表；头像菜单弹出（阅读设置 / 导入 / 全屏）；搜索框输入「雪」只剩一本《雪国》，
清空后恢复 14 行；侧栏「我的文档库」里点《金阁寺》进阅读器（大纲 6 章、工具条 8 个可点
16 个灰着）→ 点返回箭头回首页；再点行尾的 ⋯ 打开解析设置面板。
窄屏 390 / 1024 两档：无横向溢出，工具条换行，列按规则收掉。
最后 `bun run typecheck && bun run verify && bun run build` 三绿（`verify:apps` 96 项）。





### 29. 试读之后的三处返工：文案、图标尺寸、飞书也不放图（2026-09-24）

用户上手读了上一版，报回来四件事（其中三件是设计上没想清楚，不是笔误）。

**一、界面文案里的「AI 味」要清干净。** 具体点名的是一句「点一下文档就能进阅读器 ·
行尾的 ⋯ 里是解析设置与删除 · 全是本地文件，不上传」——三个毛病叠在一起：教人点按钮、
把功能罗列一遍当提示、还要顺带声明一句「不上传」。同类的还有 Office 开始屏幕底下的
「最近 3 个文件 · 点一下打开 · 右边的 ⋯ 打开解析设置」、空状态里的「拖一本小说进来，
或者点上面的「上传」」、书面板里的「用存着的原始文件重跑，不用再拖一次」。

规矩现在写在 **AGENTS.md 第一节**（那是给下一个改这个仓库的人/AI 看的），要点是：
**界面上只写「这一屏此刻是什么状态」和一个具体事实**（「还没有文档」·「已读完的没有」·
「最近 3 个文件」·「已读 42%」）；操作指南、自我说明、功能罗列、changelog 一律不写；
能删就删。想解释「为什么」就写进注释和这份 SPEC。`verify:apps` 里加了一条回归断言：
把删过的那几句列成黑名单，扫 `src/**` 里会出现给人看的那些行（跳过注释行），命中就失败——
文案这种东西没有别的办法守住。

**二、「筛选 / 显示设置」的选中态没对齐，还压到了右边的视图切换上。** 根因不是对齐，
是**类名撞车**：这两个触发器用了 `.mn-doc__tool`，而它同时是阅读器格式工具条那一格的名字。
工具条那条规则（`display: grid; width: 30px; height: 30px`）在文件里更靠后，于是首页这两个
按钮被按 30×30 的方格排；`white-space: nowrap` 的字照原样溢出格子，压在旁边的分段控件上，
看起来就像两个控件叠在一起。修法：触发器改名 `.mn-doc__viewbtn`，并把「筛选 / 显示设置 /
视图切换」三个控件包进 `.mn-doc__view` 自成一组（`flex: 0 0 auto`），谁都不许被压扁。
教训写进 AGENTS.md：**一个类名只给一个地方用**，复用之前先看另一边给它定过什么尺寸。

**三、图标普遍偏小（侧栏与阅读器都是），工具条里字体按钮和字号按钮撞在一起。**
前者是我上一轮算错了：`getBBox()` 返回的是 **user unit**（24 格坐标系里的格数），
不是像素——我把它当像素用，于是「墨迹 17 格」被我当成了「17 像素」，算出来的盒子比飞书
那边小一圈半。正确的换算是：**盒子 = 目标视觉大小 × 24 ÷ 墨迹格数**（我们这批记号墨迹只占
60% 上下，所以盒子要给到视觉大小的 1.4 倍）。照这个重新量：侧栏导航 20→24、行内文档图标
16→22（列表里 20→26）、底部 22→24、顶栏 20→24、搜索框放大镜 16→22、页签行 16→20、
排序箭头 12→22、阅读器顶栏 28→32 的按钮配 20 的图标、格式工具条 26→30 的按钮配 20 的图标。

后者是同一个病根的另一半：工具条里「字体名 / A⁻ / A⁺」这些**字形**按钮和图标按钮共用
`.mn-doc__tool` 的固定宽度 26px，字比盒子宽就溢出去压到邻居。修法是给字形按钮单独一档
（`.mn-doc__tool--text`：`width: auto; min-width: 30px; padding: 0 8px`），宽度跟着字走。
顺手修掉一个一直在的错：顶栏返回按钮写的是 `rotate-180`，屏幕上是一个**朝上**的箭头
（chevron 画的是「向下」，顺时针转 90° 才是「向左」）。

**四、飞书形态也不要显示小说图片，和 VS Code 那套一样改成 `![](./路径)`。**
做法是把编辑器用的那套图片整理提成公共出口：`lib/blocks.ts` 的 `mediaLinesHtml()`
（`prepareBody` + `media: 'reference'` 的薄封装，返回 HTML 而不是块数组），
ReaderView 在 `chrome === 'doc'` 时走它。引用行里写的是**书里的原始路径**，
靠 `resolve` 把渲染时的 blob 地址还原回去（和编辑器同一条链）。验收里断言了三件事：
正文里不再有 `<img>` / `<svg>`、引用行里的路径是原始路径、以及**原文一个字都没少**
（标题、对话、双语段、引文、图注都还在）——最后这条最要紧，这类「替换」最容易顺手吃掉东西。

**浏览器里实读过的路径**：飞书亮 / 暗两套首页整屏；筛选与显示设置展开（勾选位对齐、
18px 的间距、不再压住视图切换）；顶着 390 / 1024 / 1920 三档量图标盒子；
导入带插图的样例 epub → 逐章翻（卷首与第一章的图都成了一行 `![插图](./OEBPS/Images/…)`，
正文里 `<img>` 数量为 0）→ 阅读器工具条 24 个按钮量间距（重叠 0 处、溢出 0）→ 返回箭头方向。
`bun run typecheck && bun run verify && bun run build` 三绿（`verify:apps` 102 项）。

### 30. 快捷键表与「非编辑器形态不做演示模式」（2026-09-24）

这一轮用户报了两件事：**首页按 S 开不出阅读设置**，以及**这些快捷键都该能自定义**；
另外明确了一件以后才做的事——**演示模式在别的主题下要显示什么，先不做**。

**一、快捷键从「两个特例」变成一张表。** 上一版的 `store/hotkeys.ts` 里只有两条
（演示 `Alt+Q` / 摸鱼 `Alt+S`），而阅读器里的 `T`（目录 / 侧栏）、`S`（设置）、`F`（全屏）
是硬编码在 `ReaderPage` 的一个 switch 里的——**书架那一屏根本没有这三个键**，所以
「在首页按 S 没反应」。这一版把它们收进同一张命令表（`lib/hotkey.ts` 的 `HOTKEY_COMMANDS`，
纯数据、不依赖 zustand），每条带 id / 标签 / 默认组合 / **作用域**：

```
focused  只在没有输入焦点时响，所以可以是不带修饰键的单键（S / T / F）
global   不管焦点在哪都响，所以必须带一个真修饰键（Alt+Q / Alt+S）
```

作用域不是一个新概念，而是把上一版<两条规矩>写成了数据：全局快捷键必须带修饰键
（否则在搜索框里打一个字母就会触发），而页面里的键可以裸用单键、但要在输入框里让位。
判定的两个入口也就此固定：`useGlobalHotkeys`（两条 global，全窗口唯一监听）+
`useHotkeys` 的 `useHotkey(id, handler)`（页面自己登记，书架登记设置与全屏、
阅读器三条都登记）。**加一个快捷键 = 表里加一条 + 页面上登记一次**，
设置面板、菜单上的键位提示、冲突检查都从表里推。

设置面板多了一栏「快捷键」列这三条，两个「伪装」功能的键仍然留在各自那一栏（好对照）；
`HotkeyInput` 因此多了一个 `scope` 参数，`comboProblem(combo, scope)` 也只在这一层判断
「要不要修饰键」。菜单里那些写死的 `hint: 'S' / 'F'` 全部改成读当前生效的组合——
用户改过键之后，菜单跟着变。

**二、非编辑器主题下不做演示模式。** 用户的说法是「演示模式在不同主题下要显示不同的内容，
且用户可以自定义，目前先不做」。落到这一版就是**非编辑器形态下它彻底不存在**，而不是
「存在但不生效」：

- 阅读设置里那一栏（开关、语言、键位）只在 VS Code 那两套主题下出现；
- `Alt+Q` 也只在编辑器形态下响应（和摸鱼模式同一条规矩）——上一版它「哪儿都能按、
  但没有可见效果」，于是用户会在飞书主题下按出一个**切回 VS Code 才看得见的开关**，
  状态在你看不见的地方变了。

以后要做「每个主题一套假内容」时，改的是 `lib/decoy.ts` 与那张表，这一层不用动。

**三、验收与实测。** `verify:hotkey` 从 28 项加到 41 项：多的一段专测命令表本身
（id 不重复、默认组合不重复、每条按自己的作用域都合法、两条伪装功能必须是 global、
标签齐全），以及 `comboProblem` 在 focused 档允许单键、在 global 档仍然挡下。

浏览器里逐条按过：飞书首页按 S 打开阅读设置、再按关掉；**焦点在搜索框里打 s 不触发**；
`Alt+Q` 在飞书下不改任何状态，切到 VS Code 后照旧生效（✓ 树里出现 `notification-app`）；
把「阅读设置」改绑到 `Ctrl+K` 之后，S 失效、Ctrl+K 生效、菜单里的提示也跟着变成 Ctrl+K；
普通书架（日间）按 S 同样打开；阅读器里 T 开目录抽屉、S 开设置都正常。

顺带把重复了五处的「全屏切换」收进 `lib/fullscreen.ts`（菜单、快捷键、功能区都调用它）。
另外记一个**测量陷阱**：合成事件 `new KeyboardEvent('keydown', {...})` 默认
`cancelable: false`，于是 `preventDefault()` 无效、`defaultPrevented` 永远是 false——
用它验「快捷键有没有被拦下」会得出完全相反的结论（真实按键是 cancelable 的）。
这一轮为此白排查了一轮，验的时候要显式写 `cancelable: true`。

**四、返工：摸鱼模式的键在五套办公外壳里不响（用户报「变暗的快捷键丢失了」）。**

根因是**两处各判各的**：设置面板里「摸鱼模式」那一栏出现在所有带外壳的形态下
（编辑器 + 五套办公外壳），而它的键只在编辑器形态下响应——那条判断还是决定记录 25 写的，
当时带外壳的形态只有编辑器一个；后来五套外壳加进来（决定记录 26）把功能扩到了它们身上，
键却留在了原地。于是飞书里按 `Alt+S` 毫无反应，而面板里那个开关就在那儿。

修法是把「这个功能在哪些形态下存在」做成命令表上的一条数据（`presence`：
`editor` 只有编辑器 / `shells` 所有带外壳的形态），并给出**一个**判断函数
`hotkeyLiveOn(id, chrome)`：快捷键监听和设置面板那一栏都读它。
由此定下一条规矩：**一个功能在哪儿看得见、按得响，只能有一个定义**——
面板里有这个开关的地方，它的键就必须响；反过来也一样。

顺带补上另一半：五套办公外壳的**首页**原来根本没有压暗（`ShelfShell` 没往下传，
各首页也没盖黑纱），所以就算键响起来，在首页按也只是改了一个看不见的状态。
现在 `ShelfProps` 带上 `dim / dimOn / onToggleDim`，三处首页各自给「内容区」盖黑纱：
飞书的文档列表、企业微信的会话区、Office 开始屏幕的「最近」那一块。
企业微信功能栏上那个摸鱼按钮、Word/Excel/PPT 标题栏上那个，之前也是 `() => undefined`
的空动作（按下去没反应），一并接上了真的开关。

实测（`--mn-dim` + 截图逐点比亮度）：飞书首页 247.8 → 125.3（50% 黑纱理论值 ≈ 123.9）；
飞书阅读器、企业微信首页、Word 与 Excel 开始屏幕都按得响且真的暗下来；
普通阅读形态（日间）按 `Alt+S` 仍然什么都不做（那儿没有内容区可压）；
VS Code 那两套不受影响。首页 ⋯ 菜单里也补上了「摸鱼模式」这一项与它的键位提示。
`verify:hotkey` 从 41 项加到 48 项（新增 presence 的七条断言）。

### 31. 企业微信形态按截图一比一复刻（2026-09-24）

需求是「企业微信主题按这张图改造，一比一复刻；icon 没有就下载图标包或网上找」。

### 33. 双语书的原文段 = 聊天里的「我发的消息」（2026-09-24）

用户的第三句：「如果有存在双语的话，那么原文就在右边显示，就改成我发的消息」。

**做了什么。** 聊天形态里，双语书的**次要语言段**（解析时标的 `data-mn-lang`，也就是
对照排版里那个「原文」）现在靠右、用强调色浅底的气泡，发信人写「我」；其余照旧靠左、
写书的作者。判定就一处：`lib/chat.ts` 的 `messageSender(message, sender)`
（`message.alt ? '我' : 作者`），和 `CHAT_RAIL`、`sessionTag` 一样是纯函数、被
`verify:apps` 断言盯着——「哪几行算我发的」少写一行多写一行，盯着屏幕都未必看得出来。

**这条改的是决定记录 26 里的一句话。** 那一版写着「不把对话段染成「你自己发的」」——
它说的是**正文里的对话**（引号包起来的那种）：把书里的对白说成读者发的，那是往书里
加原文没有的立场。用户说的这一条不是那件事：染的是**书里本来就标了次要语言的段**，
而且表达的是「这一行是拿来对照的原文」，不是「这句话是读者说的」。两者不冲突，
所以 `lib/chat.ts` 里那两条注释是并列写的，不是替换。

**气泡底色没有截图可量**（参考图里全是别人发的消息），所以这一处是**算**出来的：
20% 的强调色铺在会话底上（`color-mix(in srgb, var(--mn-accent) 20%, var(--mn-reader-bg))`）。
这是「抄不到」时的退路——从注册表的颜色里派生，而不是另调一个色号；
暗色下同一条式子落到 `#22344A` 那种深蓝上，和收到的灰气泡也分得开。
**没有为它加 token**：加一个 token 每个主题都要补一个值，而这个值是可以从既有的
`accent` 推出来的（同理，文本色继续走 `--mn-alt-color`——「只看原文」时它会提回全亮，
所以朗读模式那三档的老规矩一点没变：实测 both 显示 1 条原文 + 7 条正文、primary 只留 7 条、
secondary 只留 1 条）。

**浏览器里实读过的路径**：双语样例 epub 第二章（中文正文 + 日文原文对照）——
亮暗两套各一张整屏（原文那条在右边、气泡是浅蓝 / 深蓝、发信人是「我」）、
三档双语模式来回切、以及工具条那六个按钮在 1440 与 390 两档的实量。
`bun run typecheck && bun run verify && bun run build` 三绿（`verify:apps` 119 → 121 项）。

- 裁剪标记 `#AAAAAA`：四角各一横一竖、每笔 24px、朝纸外张开
- 标题栏、页签行、桌面**是同一个色**（`#E5EBEF`），只有功能面板是白的 —— Word 这一屏连成一片
- 状态栏 `#F5F5F5`，右边是「专注 / 阅读视图 / 页面视图 / 缩放 −＋ 百分比」

**二、颜色进了注册表：`PageTokens`。** 纸边、裁剪标记、控件描边、搜索框底色这四个值是
别的 token 表达不了的（它们都是「纸」和「控件」这一层的线，不是分隔线），所以照
`ChatTokens` 的样子加了 `pageEdge` / `crop` / `control` / `field` 四个（`--mn-page-*`），
只有 `chrome: 'page'` 的两套主题要补。顺带把 `word` 那套的主 token 改成量出来的值：
`bg` `#F5F5F5` → `#E5EBEF`、`surface2` `#F0F0F0` → `#F5F5F5`。

**三、功能区的模型换了：从「一排按钮」变成「一行行格子」。** `RibbonGroup` 现在有两种写法：
老的一行式 `buttons`（Excel / PPT 还在用）和新的 `rows: RibbonItem[][]`（Word）。
`RibbonItem.kind` 说的是**这一格长什么样**——`big`（图标 38、字在下）、`small`（图标 22、字在右）、
`icon`、`text`（只有字形：B / I / U / Aa / x₂）、`rule`（1px 分隔线）、`node`（整格交给调用方：
字体框、字号框、样式库、行距那个下拉）、`column`（竖着码的一摞：剪贴板右边那三个、编辑组那三个）。
**行与行之间不对齐是照 Word 来的**：字体组第二行那排 B / I / U 本来就不和第一行的字体框对齐。

**四、标题栏、页签行、状态栏上那几个「Word 有、Excel / PPT 没有」的位置做成了可选插槽**
（`brand` / `titleTools` / `titleCenter` / `titleAlert` / `tabActions` / `statusTools`），
不传就不画——三件套仍然是同一个框，Excel / PPT 那一屏一行都不用改。

**五、「搜索」是真能搜的：`lib/find.ts`。** 标题栏正中间那个搜索框与编辑组里的「查找」指向
同一件事：**在本章里找**。全文搜索要先把每一章都读一遍（库里存的是分章 HTML，没有全文索引），
为一个标题栏上的框不值得；章内才是读者要的（「这句话在哪一段出现过」）。三条取舍：
只在一个文本节点里找（不切开正文 DOM）、**不改原文一个字**（命中处套
`<mark class="mn-find">`，清掉时把文字还给父节点再 normalize）、不搜我们自己拼进去的东西
（章末那对「上一章 / 下一章」、注音 `rt`）。`countFinds` / `markFinds` / `clearFinds` 是纯 DOM
函数，`verify:apps` 用 happy-dom 逐条断言（数得对、标记数一致、原文一个字不差、再查不套娃、
清完干净）——「标记把原文吃掉一个字」这种事盯着屏幕看不出来。

还有一条只有换主题才看得见的：**正文那块 DOM 会跨外壳复用**（html 字符串没变时 React 不重写
innerHTML），所以在 Word 里打了标记、从阅读设置里换成飞书，标记会留在正文里而搜索框已经没了。
修法是 WordApp 卸载时自己把标记清掉（一个只跑收尾的 effect），浏览器里实测过：
换成飞书之后 `mark.mn-find` 数量 0、正文 HTML 里也没有 `mn-find`。

**六、灰着的那些**：粘贴 / 剪切（只有复制是真的）/ 格式刷 / B I U S x₂ x² / 文字效果 /
高亮 / 字体颜色 / 字符底纹与边框 / 带圈字符 / 项目符号 / 编号 / 多级列表 / 排序 / 显示编辑标记 /
居中 / 右对齐 / 分散对齐 / 替换 / 选择 / 批注 / 编辑 / 评论 / 三个加载项 / 九个页签
（OfficePLUS、插入、设计、布局、引用、邮件、审阅、PDF工具箱、帮助）。每一个都有 `title`
说清为什么。样式库那五个**不是按钮**：它是文档样式的预览，画成按钮就得能按。

**七、四个只有真上手才发现的问题：**

1. **百分比 padding 是按包含块算的，不是按元素自己。** 纸的左右留白原本写 `15%`，
   结果 1906px 宽的桌面算出 286px 的内边距，正文只剩 220px（截图应该是 554）。
   改成 px（119 / 96），窄屏用媒体查询收（900px 以下 48、767px 以下 20）。
   ——这条对以后任何「按纸宽算的百分比」都成立。
2. **整条功能区不能超过窗口宽。** 九组格子加起来原本 2026px，最后两组被切在屏幕外。
   原因是每一格都宽了一档：padding `0 3px`、gap 2、**小三角改成绝对定位压在图标右下角**
   （Word 本来就是这么画的——单独排一列的话每格多占 11px）、大格 58→52、组合框与字号框各收一档，
   落回 1770px。
3. **标题栏、页签行、桌面是同一个色。** 原本标题栏用 `surface`（白），截图是 `#E5EBEF`。
   这三处按形态写 `html[data-chrome='page'] … { background: var(--mn-bg) }`；功能面板才是白的，
   上面一条浅灰线把它和页签行分开（Excel / PPT 的标题栏仍然用 `surface`——Fluent 里那一条更白）。
4. **裁剪标记是 8 条背景渐变。** 四角各一横一竖、都朝纸外张开，所以位置要写 `-24px` 与
   `calc(100% + 24px)`；`background-origin: content-box` 让它们落在**正文**的四角上
   （也就是 96 / 119 那两个留白的内侧）——一处都不用 JS 量，改留白它们自己跟着走。

**八、顺手做的几件：**

  阅读视图左边那个 = 页面视图（当前态）、放大镜 = 缩放回 100%。

**九、图标还是自己画的**（同决定记录 31 第六点）：这一轮补了 27 个（Word 商标、保存软盘、
QAT 小三角、对话框启动器、铅笔、字号 ＋/−、清除格式、替换、选择光标、字符底纹 / 边框 / 带圈字符、

**十、浏览器里实读过的路径**：亮暗两套整屏（1920×1030——纸 556..1350、正文 554、

**一、这一屏从「幻灯片浏览」改成编辑视图。** 原来用的是浏览视图（一屏贴好几张），
理由是「编辑视图在浏览器里要自己造分页、还要和进度条打架」（决定记录 27）。截图给的
就是编辑视图，所以解法是**一「页」= 一屏**：每张幻灯片占满滚动容器的高度，
`--mn-ppt-page` 由 JS 量出来写进去，上下滚动就是一张张翻，进度条仍然归 ReaderView

**二、尺寸。** 幻灯片按 16:9 塞进工作区，宽高两边同时受限，CSS 的 `aspect-ratio`
管不了这件事（一边定死时不参与另一边的计算）——所以由 JS 量：`--mn-ppt-slide`
（渲染多宽）、`--mn-ppt-scale`（缩放比）、`--mn-ppt-page`（一页多高）。版心的
**基准是 1320×743**（1920 窗口里量到的），幻灯片里的字是 `用户字号 × 缩放比`，
于是一张里的换行位置和「版心 1320」时一致，只是整体大了一号——和 PowerPoint 的

**三、版式的那两个虚线占位框。** 截图里是「单击此处添加标题 / 单击此处添加副标题」

真的字。量的数：左右各 12.35%、标题框 16%…52.2%、内容框 52.3%…76.7%。

写在竖方向会差 1.78 倍（AGENTS.md 第一节那条坑）；1em 在这个版心里恒等于 18/743 的高，
所以两个方向就统一了。框会**跟着内容长**：标题把内容往下推、内容最多长到版心底部。

**四、一条新规矩：长段落不当标题。** 一张的标题本来取「这一组的第一段」，

### 40. 阅读设置从抽屉改成全局弹窗（2026-09-25）

设置条目涨到十几条之后，贴边抽屉一整列滚着找太费劲。改成**居中弹窗**：左边竖着排大类
（主题 / 排版 / 阅读 / 演示模式 / 摸鱼模式 / 快捷键 / 高级），右边是选中大类里的细分设置。
某一类在不在仍读 `hotkeyLiveOn(chrome)`（普通形态没有演示 / 摸鱼两档，办公外壳的「阅读」
里是说明文字而不是翻页按钮）——「弹窗里有这一栏」与「键按得响」还是同一个判断。

**为什么开合要提到全局 store**（`store/settingsDialog.ts`）：触发点分散在八个形态的几十个
按钮、菜单项与快捷键上，很多还穿过了几层 `() => void` 的回调，谁开谁关各写各的写不动了；
「弹窗要从哪个按钮长出来」这件事一个 boolean 也说不清。现在只有一扇门：
**点按钮开的，出发点是刚按下去的那个元素**——弹窗从它的位置长出来（FLIP 的 First・Last・
Invert・Play，反演算术在 `lib/flip.ts`，纯函数、verify 有断言），关闭时缩回那个按钮。
触发点不一个个把元素传出来：浏览器本来就在按下时派发 `pointerdown`，store 装载时挂一个
capture 监听记下「最后一个被按下的元素」连同矩形快照（菜单项点了就卸载，事后量不到），
开弹窗时取最新的那份；键盘激活（Enter）没有 pointerdown，退回焦点元素；再没有就居中。
**快捷键（S）开的没有按钮：从屏幕中间弹出、向中间缩回**（`toggleSettingsFromHotkey`，
出发点显式置空，verify 断言这条路不走按钮快照）。关闭动画前再量一次出发点（元素还挂着
就现量，页面滚过也能缩回它此刻的位置；摘掉了就用按下时存的快照）。

组件上的三条硬经验：

1. **居中不能用 CSS transform。** WAAPI 的 transform 关键帧会整个替换掉 CSS 的
   `-translate-x-1/2`，弹窗会跳到右下角。外层 `grid place-items-center`，面板自己
   `transform: none`，FLIP 才算得干净。
2. **离场收尾不能只靠 `onfinish`。** 动画时钟在后台标签页里可能不推进（内嵌浏览器里
   实测一帧不走），`onfinish` 永远不来弹窗就赖着。收尾做成幂等的（`animRef` 认主），
   `onfinish` 和 `duration+80ms` 的定时器谁先到都行；重开（cancel）之后就不许再收。
   时长与缓动从 `--mn-dur-*` / `--mn-ease` 现读，`prefers-reduced-motion` 直接 0ms。
3. **窄屏先把骨架转成上下结构。** 弹窗在 390px 铺满，左边大类横过来变一排可横滑的页签；
   外层容器要跟着 `max-md:flex-col`，否则 `w-full` 的页签行把内容区挤成零宽。

焦点进弹窗（键盘读者的 Tab 从这儿开始），关的时候还回去；Esc 的规矩和 Panel 一条
（`data-mn-esc-local` 的下拉先归下拉）。旧的 `SettingsPanel` 删了，目录抽屉（TocPanel）
仍是抽屉——它是导航不是设置，贴边扫目录比居中合理。`verify:apps` 加了 9 项
（241 → 250）：反演后中心落回按钮中心、比例即矩形之比、快捷键那路 `scale(0.92)` 无位移、
按下后出发点是那个按钮、快捷键开 `origin === null`、触发元素卸载后仍缩回快照位置。

### 41. 弹窗落地后的四件返工（2026-09-25）

用户试到的是四个问题，逐条修：

**一、收尾闪帧 → 动画换 Motion。** 手写 WAAPI 的离场在播完那一拍会把元素弹回
自然样式（fill 为 none），等 React 卸载的那一帧就是用户看到的「闪一下」。
动画引擎换成 **Motion**（`motion/react` 的 AnimatePresence）：离场时它把终态钉在
元素上、播完才卸载，这类闪帧从结构上不存在。选型只取 Motion 一个库——AutoAnimate
做不了「从矩形反演」的定制动画，GSAP 与它完全重叠，两个都不引。FLIP 的算术仍是
`lib/flip.ts` 的 `flipStep`（中心锚点：弹窗用 `inset-0 + margin:auto` 居中，不占
transform），尺寸改成 JS 一处算好内联进去（`dialogSize()`），否则比例的分母量不到。

**二、换主题后弹窗向中间收。** 在弹窗里选主题 = 整个外壳都换了，原来的触发按钮多半
不在了，缩回按钮反而是错的。store 加 `closeSettingsToCenter()`（`exitCenter` 标记，
下次打开复位），选主题后调它。**有个前提**：弹窗必须挂在**页这一层**而不是阅读器的
某个分支里——换主题会让 ReaderPage 的三个分支、ShelfPage 的三个书架互相切换，
弹窗挂进分支就跟着卸载，离场动画根本没机会播。顺带踩出一个接线 bug：
编辑器分支写成了独立的 `if + else`，办公外壳的 shell 赋值会被普通分支覆盖——

### 44. 接入 Tauri，Windows 桌面端（2026-09-25）

同一份前端，现在有两种跑法：浏览器里的 PWA，和 `src-tauri/` 装出来的 Windows 桌面程序。

**为什么是 Tauri 不是 Electron。** 这个应用的全部资产（解析器、主题、书架）是静态资源，
壳只需要「一个窗口 + 一个现代 WebView」。Windows 10/11 自带 WebView2，Tauri 的壳只有几 MB；
Electron 要自带一份 Chromium，安装包和内存都是几十上百 MB 的起步价。代价是 Rust 工具链——
但壳里没有任何业务逻辑，`lib.rs` 只有启动窗口一行，维护面很小。

**前端零改动。** 不引 `@tauri-apps/api`。文件导入用的 `<input type=file>` 与 HTML5 拖放
在 WebView2 里原样工作（拿到 File 对象就有字节，本应用从头到尾不需要真实路径）；
书在 IndexedDB，WebView2 有自己的持久化用户数据目录；封面/插图的 blob URL 也照常。
唯一的分流点在 `vite.config.ts`：Tauri 的钩子带着 `TAURI_ENV_*` 环境变量跑 vite，
借它跳过 PWA 插件——

1. **桌面构建不注册 Service Worker。** SW 是给浏览器补「离线外壳」的，桌面端资源就在
   exe 旁边，没有离线问题要解；反过来 SW 会把外壳缓存进 WebView2 的用户数据目录，
   应用更新之后还在放旧壳。没有 SW，`navigateFallback` 的活由 Tauri 的资源解析器接：
   生产模式下对找不到的路径最终回落 index.html（`tauri/src/manager/mod.rs` 的 `get_asset`），
   所以 `createBrowserRouter` 在桌面端 F5 刷新 `/read/:id` 不会 404——这是查过源码才敢留的。
2. **`dragDropEnabled: false`。** Tauri 默认在窗口层接管文件拖放（为的是把真实路径递给
   Rust 侧），接管之后 WebView2 的 drop 事件就不再触发，书架的拖拽导入会整个失效。
   关掉它，事件回到 `useFileDrop` 手里。

**窗口与打包。** 默认 1280×800（最小 900×560），标题 MioNovel。打包目标只留 NSIS
（SimpChinese）：MSI 要再拉一套 WiX 工具链，发布一个就够。窗口图标由 `bun run icons:desktop`
从 `public/MioNovel.png` 派生——源图不是正方形，脚本先补透明边再交给 `tauri icon`；
注意 sharp 的管线顺序是固定的（resize 先于 extend），补边和缩放必须拆两步，
否则出来的不是正方形。`tauri.conf.json` 的 `version` 与 package.json 的手抄对齐，
发版时两处一起改。

**命令**：`bun run app:dev`（起 vite + 桌面窗口，vite 端口被占会直接报错而不是静默换端口——
devUrl 写死了 5179）、`bun run app:build`（出 exe + NSIS 安装包）。

### 45. 便携版、MSI、安装器的脸面（2026-09-25)

接上一条，把桌面端的三个分发形态补齐。

**便携版是同一个 exe 加一个标记文件。** 没有编第二个「便携版二进制」：exe 启动时看自己
旁边有没有 `portable.txt`（`src-tauri/src/lib.rs` 的 `portable_data_dir`），有就把 WebView2
的用户数据目录指到旁边的 `data\`。书、进度、阅读设置全在那个目录里——它们本来就不是
Rust 侧存的，是 WebView2 的 IndexedDB/localStorage，所以挪这一个目录就等于全挪了。
这条路走的是 `WebviewWindowBuilder::data_directory`：Tauri 在 Windows 上默认强制把数据目录
设成 `%LOCALAPPDATA%\<identifier>`（`tauri/src/manager/webview.rs`「force a data_directory」），
但注释明说「we do respect user-specification」。窗口因此改成 `create: false` + setup 里
`from_config` 手动建——配置里的 `dataDirectory` 字段要求相对路径且按 `%LOCALAPPDATA%` 解析，
表达不了「exe 旁边」，只能走 builder。便携版运行时 C 盘零写入；前提是 WebView2 运行时
已在系统里（Win10/11 自带，它是系统组件，不算本应用落的文件）。

**MSI 是一行 targets 的事。** `bundle.targets` 从 `["nsis"]` 改成 `["nsis", "msi"]`，
WiX 工具链由 CLI 首次构建时自动下载。MSI 默认机器级安装（`C:\Program Files\MioNovel`，
UI 可改目录），和 NSIS 的用户级并存，发布时按场景二选一即可。

**安装器之前用的是 NSIS 默认图标，不是没人注意，是没配。** 把旧 setup.exe 的图标提出来
一看：地球加蓝箭头，NSIS 的默认脸。bundler 不会自动拿 app 图标当安装器图标，必须显式给
`installerIcon` / `uninstallerIcon`（指 `icons/icon.ico`）；顺手把两张品牌位图也配了——
`headerImage`（150×57，每页头部）和 `sidebarImage`（164×314，欢迎/完成页侧图），由
`bun run icons:desktop` 从 MioNovel.png 派生（`scripts/make-desktop-icons.ts`）：白底居中
logo、底部一条深青加珊瑚的双色条，颜色取自 M 的笔画；sharp 不认 BMP，脚本里手写了
24 位 BMP 的编码（未压缩 BGR、行序自下而上、行宽补 4 字节）。

### 46. 小窗模式：悬浮在所有软件上面的第二窗口（2026-09-25）

桌面端独有：阅读设置里开了小窗，一个 340×520 的无框窗口落在你挑定的屏幕角上，
层级永远最高。它平时是**藏着的**——鼠标挪进它占的那块屏幕区域才显示，离开立刻藏回去。
开它的场景就是「在别的软件里干活时顺便读几行」，所以每个细节都围着「别打扰正事」转。

**「默认不显示 + 悬浮显影」做在 Rust 这边，靠轮询不靠事件。** 一个隐藏的窗口在 Windows
上根本不参与命中测试，没有事件可听；反过来一个显示着的透明窗口，透明区域照样吃掉鼠标
（WebView2 的 HWND 是矩形）。所以：窗口平时 `visible: false`（不挡任何点击），
Rust 侧一个 120ms 的轮询线程拿 `cursor_position()` 对着窗口矩形比——进了就 show、
出了就 hide。「立刻消失」因此没有延迟，也永远不会有「看不见却挡着点」的窗户。

**窗口绝不抢焦点。** show() 在 Windows 上是 SW_SHOW（会激活）——悬浮窗一闪，
你正在打字的那个软件就失焦了，这是致命的。创建后补 `WS_EX_NOACTIVATE`（顺带
`WS_EX_TOOLWINDOW`，不进 Alt-Tab）：ShowWindow 不再激活，鼠标滚轮照常滚给悬停
窗口（Win10 起），点击照常送达，前台窗口全程不动。小窗里因此没有输入框，也不需要。

**前端零 Tauri API 的规矩有一条受控的例外。** 数据与文件照旧不经过任何 Tauri API；
但窗口的显隐、置顶、系统级快捷键只有壳管得了。桥只有两个命令：主窗口把设置
`invoke('mini_apply', { config })` 推给壳（开关、落角、快捷键）；壳收到系统快捷键
按下时置一个标志，前端每 500ms `mini_take_toggle` 来取（取走即清）。**不走事件
通道**：listen 的订阅时序、权限、事件名校验排障成本太高，而这个壳本来就在轮询
光标，多扫一个标志位不值一提。开关状态只有 `store/mini` 一份，壳只是执行人。
调用走 `app.withGlobalTauri` 注入的 `window.__TAURI__`（`lib/desktop.ts`），**不引**
`@tauri-apps/api` 包，浏览器里全部静默不动作。小窗是第二个 webview，必须指向
**同一个** WebView2 用户数据目录（便携模式同理），IndexedDB 才是同一份——
不然小窗书架是空的。

**两个一踩就死的坑，都藏在「窗口操作必须在 async command 里做」。** 其一，同步
command 跑在主线程上，而建窗、定位、查位置都要经 dispatcher 等事件循环应答——
主线程等自己，`mini_apply` 永远不返回，悬浮轮询线程的每个查询也跟着饿死；
表象是「窗口建出来了但永远在默认位置、永远不显示」，`mini_apply` 改成 async 才通。
其二，GUI 子系统（windows_subsystem=windows）下 stderr 句柄无效，诊断不能写
`eprintln!`——它失败即 panic，会把整个 command 炸掉；壳里统一用
`mini.rs` 的 `log()` 写进 `%TEMP%\mionovel-mini.log`。

**同一份前端装两次。** 小窗加载同一个 index.html，壳的 initialization_script 塞
`window.__MN_MINI__`，main.tsx 据此渲染 MiniApp 而不是路由。里面只有两个视图：
书架是**一列文字**（`miniShelfBooks` 只列 `state: 'ready'` 的书——importing/error
是半成品；最近读过的在最上面），正文是上下滚动、滚到章尾接着滚就是下一章。
进度写同一张表，主窗口和小窗互相接得上。

**「只有常规主题才有小窗」的判断只有一个函数。** `store/mini` 的 `miniAvailable(themeId,
desktop)`：桌面端 + 全局主题是普通阅读形态。设置弹窗里那一栏的出现条件与推给壳的
enabled 用它——主题切到外壳主题时窗口整个收起（设置留着，切回来自己恢复），面板里
有开关、壳上没窗户这种分裂不会出现。

**开小窗 = 主窗口自动藏起来，这是这个功能的一半意义。** `apply_windows`（三条路共用：
前端推配置、快捷键在壳里翻转、小窗里的「放大」按钮）：开小窗前把主窗口 `hide()`——
任务栏里像没有这个应用；关小窗时主窗口 `show()` + 抢回焦点。小窗头部右侧有一个
**放大按钮**：`mini_request_restore` 直接还原主窗口、关掉小窗、把配置翻回关，再置一个
restore 标志让主窗口的轮询把设置同步回关——窗口行为不等待任何轮询，因为**主窗口藏着
的时候，浏览器把它的定时器节流到 1s 起**，等轮询再翻就太慢了；这也是快捷键按下时壳
直接在 Rust 侧翻转配置的原因。轮询（`mini_take_events`，取走即清）只负责让 store 跟上。

**透明度与变暗是小窗自己的设置**（`store/mini` 的 `opacity` / `dim`），不经过壳：
前者是根元素的整体不透明度，后者是盖在内容上的黑纱（摸鱼模式那层纱的思路，
`pointer-events: none` 不挡按钮）。两个滑条在小窗模式那一栏里。

**「离开立刻消失」是两条腿**：壳的 120ms 光标轮询兜底，小窗自己的 `mouseleave`
（`mini_hide_now`）事件驱动零延迟——鼠标一出去窗口就没了，没有过渡动画可看。

**窗口大小归用户**：小窗 `resizable(true)`（tao 对无框窗口做边缘命中测试）+ 建窗时
**必须 `auto_resize()`**——webview 默认不随窗口伸缩，不开它，窗口缩了页面还卡在
建窗尺寸。用户拖出来的尺寸由轮询线程每拍直读 OS（Windows 上 `GetWindowRect`，
绕开 dispatcher 的 outer_size——它是排队的异步应答，拖拽刚结束会拿到滞后的旧值，
同一拍两次调用能读出不同结果）与 last_size 对账，变了就落盘到数据目录的
mini-size.json（跨重启）；建窗尺寸的优先级：会话内拖过的 > 落盘的 > 内置默认。
**页面的 innerWidth/innerHeight 在模态拖拽循环里不更新、resize 事件也不派发**
（WebView2 实测），别指望 JS 上报；resizable 之后钳制范围（宽 240–800、高
320–1200）写在壳和 store 各一份即可，但**别把宽的 max 给高度用**——高度被钳到
最少 800，拖出来的新尺寸永远「无变化」，对账不落盘（踩过，排查了一下午）。
禁用小窗是 `hide()` 而不是销毁：窗口活着，用户拖的尺寸、读到的章节天然都在。

**小窗里滚到章尾就停在章尾**：滚轮不做章与章的跳转（主阅读器的翻页键才管换章），
换章用头部那对按钮。这是刻意的——「一直往下滚被拽去下一章」对小窗的碎片阅读
太打扰。

**试用返工（同日）：「关了还在」「关软件后进程残留」与全主题开放。**
其一，poll_hover 的「关闭状态兜底隐藏」分支在历次改动中被挤丢了——`mini_apply`
hide 一次，下一拍轮询又按旧逻辑 show 回来，用户怎么关小窗都「还在」；恢复
`if !enabled { hide; return }` 后每拍按死关闭状态。其二，主窗口关闭＝整个应用退出
（`CloseRequested` → `app.exit(0)`）：小窗是附属窗口，主窗口没了它不该拖着进程
继续悬浮。其三，主题限制解除：任何主题都能开小窗，`miniAvailable` 只看桌面端——
小窗的视觉本来就直接沿用全局主题令牌，亮色主题下是亮的、暗色下是暗的，
不需要（也不应该）按主题白名单。
排查中顺带实锤两条 dispatcher 的坑：**非主线程的窗口查询（scale_factor 返回 1.0、
monitor 返回 None）会静默降级**——查询类一律直调 Win32（GetWindowRect /
GetMonitorInfoW / GetDpiForWindow），dispatcher 只留操作类（show/hide/set_position）；
**`window.hwnd()` 拿到的是 webview 子窗口**，对它做 Win32 显隐只藏得到内容、
藏不到真正的顶层窗口——显隐走 dispatcher 的 show/hide 才是对父窗口的。

**主题不跟随与渐隐的修复（同日二轮返工）**：重开的小窗还是旧主题——
WebView2 的 localStorage 跨进程可见性有延迟，销毁重建的小窗从 localStorage
初始化会读到旧值。修法是**不走 localStorage**：mini_apply 随配置带上全局
theme_id，壳在建窗的 initialization_script 里注入（页面任何 JS 之前执行，
首帧即正确主题），页面挂载后再 `mini_ready` 主动拉一次（建窗早期的 eval
会落在还没挂好 handler 的页面上被丢掉）；运行中的主题变化由壳 `eval` 注入
`window.__MN_APPLY_THEME__`。「消失时的过渡动画」实测为 hide 排队延迟叠加
透明度/变暗设置的静态外观——显隐改走 Win32 顶层窗口直调（`window.hwnd()`
取 `GetAncestor(GA_ROOT)` 归一到顶层再 ShowWindow）后瞬时消失。

**小窗开关是系统级快捷键，登记方式和页面命令不同。** 它要在别的软件是前台时也响，
所以不在任何页面登记（useHotkey / useGlobalHotkeys 都没有它），由壳经
`tauri-plugin-global-shortcut` 注册。但它**仍在命令表里**（lib/hotkey.ts 的
`mini-window`）：设置 UI（HotkeyRow）、默认值、冲突检查都从表里推，这是表作为
唯一事实来源的延伸。组合变了壳全拆重挂；某一串认不出来只跳过那一串。


### 47. 冲突键显形、无框窗口、托盘与滚动的记忆（2026-09-26）

五件用户报的事，一次落地：快捷键冲突要从「录的时候挡住」改成「看得见的红字 +
真的失效」；桌面端非常规主题把原生标题栏收掉、窗口三钮挪进外壳顶栏；设置弹窗
记住你看到的地方；「关窗」多一档「藏进托盘」；飞书主题书架的标题在默认窗口
宽度下整列消失。

**冲突：不拦，显形，两边都停。** 原来的做法是录键时查一遍「这个组合已经给了
某功能」然后拒收——用户永远不知道「原来这两处能撞」，而且存档迁移、命令表
改版都可能留下拦不住的冲突。现在判定搬进 lib/hotkey.ts 的三个纯函数
（`conflictOwners` / `conflictedCombos` / `conflictLabels`，verify:hotkey 逐条
断言）：录键照收，chip 标红，chip 底下一行字报出「和谁撞了」（T 和「目录 /
侧栏」绑的是同一个键，这两处都停用了）。**运行时三处共用同一份判定**：
`useHotkey`、`useGlobalHotkeys` 把冲突串从生效组合里剔除，`useMiniWindow`
推给壳的系统级快捷键同样剔除——同一个键不能页面里停用、系统里照响。冲突的
是一**串**，不是整条命令：命令的其他键照常生效。出厂默认表必须无冲突
（verify 断言），否则用户开箱就是红的。

**无框窗口：决定点在「应用主题的地方」，不从 DOM 反推。** 非常规主题
（七套外壳形态）把原生标题栏收掉，最小化 / 最大化 / 关闭挪进外壳顶栏——
那一条本来就是窗口的标题栏，再叠一条原生的是重复；普通阅读形态还原带边的
窗口。第一版用一个 MutationObserver 盯 `<html>` 的 data-chrome，结果在
StrictMode 下「新挂载的组件读属性、effect 写属性」的先后对不上：主题切回
外壳形态的那一拍，新观察器错过唯一一次变化，窗口钮从此消失。修法是把收放
的决定点放进**应用主题的那两处**（useGlobalTheme / useScopedTheme 调
`syncWindowDecorations`）：主题在哪应用，`set_decorations` 就在哪推，不设
第二份事实来源。窗口三钮（ui/WindowControls）只会被七套外壳的顶栏渲染——
外壳挂着，形态就必然不是 plain——所以它只需要排除浏览器和小窗，不需要知道
当前形态。顶栏拖拽（`window_drag`）与双击最大化走自己的命令而不是官方
drag region：官方那套要为 `plugin:window` 开一整套 capability，我们的壳
本来就一直给自定义命令。三条窗口命令（`set_decorations` / `window_minimize` /
`window_toggle_maximize` / `window_drag` / `window_close`）全部 async——
同步 command 跑在主线程上等事件循环应答会死锁（小窗那边的老坑，见 46）。
**`set_decorations(false)` 之后 `GetWindowLong` 里 WS_CAPTION 位仍在**
（tao 用 WM_NCCALCSIZE 把非客户区算成零，不是清样式位），验证标题栏收没收
要看屏幕，别看样式位。

**关窗的两档 + 托盘。** 设置-高级里「关闭窗口时」：退出程序（默认，关窗即退、
小窗一起退——小窗是附属窗口）；隐藏到托盘（窗口藏进通知区，托盘图标能找回）。
**小窗开着时关主窗只能藏**，这是壳的硬规矩、不归设置管：退出会把悬浮的小窗
一起带走。托盘常驻创建、按需显隐（`sync_tray`：关窗会藏或小窗开着才可见——
用户选了「关窗即退」且没用小窗时，通知区不挂死图标）；左键单击 = 回主窗口
（小窗开着时走 `reveal_main`：收小窗、还原主窗、置 restore 标志让设置同步回关），
菜单里「打开 / 退出」。原生标题栏的 × 与外壳顶栏的「关闭」（`window_close`）
落到同一个 `handle_main_close`。托盘需要 `tauri = { features = ["tray-icon"] }`。

**设置弹窗的滚动记忆只活在本次进程。** 右侧内容那一栏按大类记 scrollTop
（store/settingsDialog 里的一个 Map，滚动时记、打开与切换时取）——关掉再开
停回你上次看到的地方。故意不持久化：「记住看到哪」是本次使用的顺手，不是
跨重启的设置。

**飞书书架的标题列是被四列数据挤没的。** 默认 1280 的窗口下，位置 / 所有者 /
创建时间 / 最近访问各 224px 加行尾 34px，正好把 `minmax(0, 1fr)` 的标题列
压成个位数像素——「每行都没有标题，拉宽窗口才回来」。修法是把「显示哪几列」
从窗口宽度的媒体查询改成**列表容器的实测宽度**（ResizeObserver 量
`.mn-doc__table`）算出来：标题列先保住 260px 底线，剩余宽度按 最近访问 →
所有者 → 创建时间 → 位置 的次序把数据列依次请上桌（位置那列每行都是同一个
值，最先让路）。判定是纯函数 `docListColumns`（lib/appdocs.ts），
verify:apps 用 1280 / 1920 / 560 / 逐宽度扫描断言它。桌面端的 dev 容易踩
一个无关的坑顺带记下：`app:dev` 的 vite 监视整个工作区（含 src-tauri/target），
cargo 重链接 DLL 时监视器会 EBUSY 崩掉——先 `cargo build` 把构建做热再起
`app:dev`。

**托盘挂着也该是「睡着」的：TrySuspend（同日三轮）。** 用户拿网易 UU 远程对比：
同样是 WebView2，人家托盘里只有三十来 MB，我们 420MB。差别就在「宿主有没有主动
挂起」——WebView2 不会因为窗口隐藏就自己省内存，渲染进程的 JS 堆、缓存、封面
纹理原样驻留，得宿主调 `ICoreWebView2_3::TrySuspend` 才放。现在 `hide_main_window`
（关窗藏托盘、开小窗藏主窗，两条路共用）藏完窗口就把主窗口的 WebView2 挂起，
`show_main_window`（托盘单击 / 菜单 / 小窗放大 / 关小窗，所有回主窗口的路径
都收拢到这里）先 `Resume` 再显示。实测挂起 + 半分钟后：420MB → **26MB**，
比 UU 远程还低。三个一踩就瘸的坑：

1. **`WebviewWindow::hide` 只藏 tao 窗口，不碰 WebView2 控制器的 IsVisible**——
   控制器仍认为可见，TrySuspend 的「WebView2 必须不可见」前置检查当场失败，
   内存一分不降。要在 with_webview 闭包里自己补 `controller.SetIsVisible(false)`，
   恢复时对称置回 true。
2. **TrySuspend 是异步的，内存释放滞后几十秒**——刚藏完那一拍量 working set
   还是 130MB，等半分钟才掉到 MB 级，验收别在头几秒下结论。
3. **挂着调试器（DevTools / remote-debugging-port）时 TrySuspend 直接失败**——
   带调试口验收看到「没生效」是假的。诊断走 mini.rs 的 log()（TrySuspend 的
   HRESULT 结果写进 %TEMP%\mionovel-mini.log）。

挂起中的页面不跑 JS：主窗口那 500ms 的标志轮询（mini_take_events）也随之停摆，
无妨——窗口行为都在壳里即时做，主窗口回来（Resume）后第一拍把标志补同步。
「退出程序」路径不走挂起，直接 `app.exit(0)`。

**最小化也挂起 + 双击手感的修正（同日四轮）。** 用户拿任务管理器对比：前台使用中
我们 132MB（浏览器进程 35 + GPU 36 + 渲染 49 + 工具 10），UU 远程 31MB。结论
先讲清楚：**前台可见时的下限是 WebView2 自己的固定开销**（浏览器 + GPU + 工具
进程 ≈ 80MB，任何应用都要付），UU 的 31MB 是「渲染进程挂起 + 页面极小 + 长期
闲置被系统换出」的产物——它的渲染进程常年 3.8MB、挂着效率模式徽章，说明它平时
根本不在渲染（主界面是原生的，WebView2 只当辅助）。所以两条腿：

1. **后台能压的压到底**：最小化的主窗口在 10 秒后自动挂起（MINIMIZE_SUSPEND_DELAY，
   poll_minimized 由既有 120ms 轮询驱动），还原即 Resume。实测 350MB → 16.5MB。
   状态只有 main_trimmed 一个 AtomicBool，托盘/小窗/最小化三条路（lib.rs 与
   poll_minimized）读写同一个。**poll_minimized 只管「可见但最小化」**：藏进
   托盘/小窗的窗口 IsIconic 恒为 false，这里若插手会把托盘的挂起又恢复回去
   （判断条件里必须先排除「窗口已隐藏」）。
2. **前台是「正在渲染的应用」**，渲染进程 49MB 里是 React 全家 + 书籍数据 +
   封面位图，highlight.js 早已按需加载、解析器早已分块——能懒的都懒了。
   剩下的是浏览器/GPU 进程的地板，压不进 30MB，除非整个界面不渲染。

**标题栏文字不可选中，双击才不会被选字抢走。** 七套外壳顶栏本就该是
`user-select: none`（窗口的一部分，不是内容），此前 doc 首页与 desk 顶栏漏了，
补齐。双击最大化**不监听 dblclick 事件**：第一下 mousedown 已经让壳进入拖拽的
模态循环，dblclick 常被它吃掉；改为在 mousedown 里自己判——两次按下间隔
小于 400ms 就是双击（切最大化），否则当拖拽起点。与原生标题栏同一手感。
