# MioNovel 设计说明

这份文档记录的是**为什么这么做**。代码能告诉你它怎么运行，但告诉不了你当初为什么否掉另一种做法——
过几个月你要加功能时，那些理由比代码更值钱。

README 讲怎么跑和怎么用，这份讲决定与理由。

---

## 一、定位

本地优先的小说阅读 PWA。导入自己的 txt / epub，存在浏览器的 IndexedDB 里，离线可读，没有后端、没有账号。

三个前提决定了后面几乎所有选择：

1. **本地是唯一副本。** 所以原始文件必须原样存着（能导出、能重新解析），并且要申请持久化存储。
2. **用户的书是五花八门的。** 中文老 txt 是 GBK、繁体是 Big5、epub 是别人用什么工具生成的都有。
   解析层的第一目标是「尽量读懂」，第二目标才是「读得快」。
3. **要长期阅读，不是看一次。** 排版、主题、进度恢复的体验比功能数量重要。

## 二、技术选型

| 选择 | 理由 |
|---|---|
| Vite + React + TS | 与同目录的 MioNote 保持一致，同一套工具链 |
| Dexie 4 | 类型化的 IndexedDB 封装；`useLiveQuery` 让书架自动跟着数据变，不需要手动 invalidate |
| zustand + persist | 阅读设置只有几百字节，localStorage 够用；书和章节进 IndexedDB |
| Tailwind CSS v4 | CSS-first，`@theme inline` 能把语义 token 直接接到工具类上——这是主题系统的基础 |
| fflate | 零依赖的 zip。替代 jszip：EPUB 只需要「一次解出一个 ArrayBuffer 里的所有条目」，fflate 更小更快 |
| chardet | 纯 JS 的编码识别，零运行时依赖 |
| dompurify | 属性白名单、URL 校验、mXSS 这些深水区交给它（但见第七节的第二层说明） |
| vite-plugin-pwa | Workbox 封装，precache app 外壳就够 |
| **不用** epub.js | 见下 |

### 2.1 为什么不用 epub.js（2026-09-22 决定）

原本的计划是用 epub.js，最后改成了自研解析。改变主意的不是「epub.js 不好用」，而是两件事：

**一是 koodo-reader 的实际做法。** 它是这个领域最成熟的开源阅读器，而它的依赖表里**没有 epubjs**。
它自己写了一个 EPUB 引擎（`kookit`，以 533KB 压缩产物 vendored 进仓库），里面的 book 对象刻意模仿了
epub.js 的数据结构（`manifest` / `spine` / `sections` / `toc` / `resolveHref`），底层用 JSZip 解包。
换句话说：最需要它的人，最后选择了重写。

**二是它的价值集中在 iframe 上，而 iframe 正好挡住我们要的东西。** epub.js 的核心是 `Rendition`，
它把正文渲染进一个 iframe——分页、CFI、主题 API 都建立在这个前提上。而 CSS 自定义属性不跨 iframe 边界，
于是主题要么注入第二份（在 iframe 里重新拼 CSS 字符串），要么维护两套。epub.js 的依赖树也不小：
`jszip + lodash + core-js + localforage + path-webpack`，而且版本停在 2023 年。

自研解析的代价大约 300 行（目录、图片路径重写、封面回退链、spine 归并），换来的是：

- 一套排版：TXT 和 EPUB 走同一组 CSS，因为都归一化成「章 HTML」；
- 一套主题：变量直接级联到正文，不需要第二份 CSS；
- 一套进度：章序号 + 章内比例，两种格式通用；
- 没有 iframe：划词、注解、全文搜索这些后续功能的门是开着的。

**这条决定是可逆的。** `parsers/types.ts` 里的 `BookParser` 接口就是为它留的：想把 EPUB 换成 epub.js，
写一个实现注册进去即可，数据层和阅读器不用动。

### 2.2 参考 koodo-reader 的许可边界（重要）

koodo-reader 与它的渲染引擎 kookit 都是 **AGPL-3.0**（`package.json` 里没有 license 字段，以 LICENSE 文件为准）。

本项目**只借鉴架构思路，代码全部自己写**，没有从它那里复制任何代码。借鉴的是三个想法：
每本书独立的解析规则与「改规则后重新解析」、每本书独立的样式设置、自定义 CSS 逃生口——
这三个都用我们自己的方式实现（见 `BookPanel.tsx`、`store/settings.ts`）。

明确**没有**借鉴的是它的主题系统与安全模型：它没有 CSS 变量、没有主题对象、没有注册表，
判断暗色靠把背景色和字面量 `"rgba(44,47,49,1)"` 做字符串相等比较；正文净化依赖单一机制。
这两处恰好是本项目要做对的对方（第五、七节）。

## 三、分层：解析 → 存储 → 渲染

```
文件 → [解析层] parsers/ → ParsedBook → [存储层] db/ → [渲染层] 阅读器
        每格式一个实现      归一化模型      Dexie      只认归一化模型
```

`BookParser` 是整个应用的契约：

```ts
interface BookParser {
  format: BookFormat
  detect(head: Uint8Array, fileName: string): boolean   // 看 magic bytes，不信后缀
  probe(file: File, options): Promise<FileProbe>        // 便宜地看一眼
  parse(file: File, sink: ParseSink, options): Promise<ParsedHead>
}
```

两个约定值得单独说：

**一、章节通过 `sink.onChapter()` 逐章交出去，解析器自己不保留全书。** 这是「30MB 的 txt
峰值内存只有单章 + 一个解码缓冲」的前提。如果把 `ParsedChapter[]` 作为返回值，解析器就必须把整本书
留在内存里，大文件会直接把标签页撑爆——koodo-reader 的 TXT 路径就是那样：全量 decode →
`split("\n")` 整个行数组 → 再拼成整个 HTML 字符串。

**二、`BookParser` 按需加载。** txt 和 epub 的解析要用到 chardet / fflate / dompurify（约 90KB），
而打开书架、读一本已经导过的书完全不需要它们。做成动态 `import()` 之后，主包从 182KB 降到 150KB（gzip）。
连 `MANUAL_CHARSETS` 都单独放在 `charsets.ts`（不依赖 chardet），就是为了不让书架上的一个编码下拉框
把编码检测库拉进主包。

## 四、数据层

### 4.1 为什么是五张表而不是一张

```
books      id / 元数据 / 进度 / 章数与字数前缀和 / 卷分组节点
files      bookId, 原始文件 Blob（原样）
chapters   [bookId+index], 章节 HTML
toc        [bookId+index], 只有标题、层级、字数
resources  [bookId+path], epub 里抽出的图片
```

- **`files` 与 `books` 分开**：书架渲染时整表读 `books`，如果原始文件也在里面，几十 MB 会被顺手反序列化出来。
- **`toc` 与 `chapters` 分开**：目录抽屉需要**全部**章节的标题，而 `chapters` 每行都带着那一章的完整 HTML。
  一本 3000 章的书整表读出来是十几 MB，只为了拿 3000 个标题；`toc` 把这份代价压到几百 KB。
- **`resources` 单独存图片**：章节 HTML 里图片是 `mnres://` 占位，渲染当前章时才取出来换成 ObjectURL，
  离开就 revoke。打开一章完全不碰 epub 原文件，内存占用只跟当前章有关，跟书有多大无关。

对照：koodo-reader 用 localforage 存**五个巨大的数组**，每次保存一条笔记都要读出整个数组、改完再写回去；
封面 base64 内联在 `books` 数组里；阅读进度存在 localStorage。这三条我们都避开了。

### 4.2 进度模型

```ts
progress = { chapterIndex, ratio }      // ratio 是章内比例 0-1
```

全书百分比靠导入时算好的 `charOffsets`（每章起始字数的前缀和）O(1) 算出：

```
已读字数 = charOffsets[i] + (charOffsets[i+1] - charOffsets[i]) * ratio
```

滚动模式的 ratio 来自 `scrollTop / (scrollHeight - clientHeight)`，翻页模式来自 `(page+1) / totalPages`。
两种模式、两种格式存的是同一个量，所以切换阅读模式或重新解析都不会让进度错位，也不需要格式专属的定位字段。

**章节字数只数正文，不数我们自己包上去的 HTML 标签**——否则段数多的书会被系统性高估，百分比跟着偏。
这个 bug 在写 TXT 解析时出现过一次（`countChars(html)` 把 `<p></p>` 也算进去了）。

### 4.3 导入流水线

```
1. 签名去重（name + size + lastModified）
2. 判定格式 → 按需加载解析器
3. probe：编码、将采用的分章规则、前几个章标题
4. **先落盘**：写 books（state: 'importing'）+ files
5. 解析，章节按 50 章一批 bulkAdd
6. 成功 → state: 'ready' + 章数/字数/前缀和/卷分组；失败 → state: 'error' + 中文原因
```

**先落盘再解析**是关键：中途失败或浏览器崩溃都不会丢原始文件，用户可以重试或改规则重新解析，
不用再拖一次文件。启动时的 `cleanupStaleImports()` 会把上次崩溃留下的 `importing` 记录收尾成 error
（靠内存里的 `inFlight` 集合区分「残留」和「这次正在跑的」）。

**没有导入前的确认弹窗。** 识别结果写进书里，书架上直接显示解析后的样子，觉得不对就在「解析设置」里改，
改完原地重新解析——比让用户在没看到结果之前先确认编码合理。

## 五、主题系统

### 5.1 做法：注册表是唯一事实来源，切换只改一个属性

```ts
interface ReaderTheme { id, name, scheme: 'light'|'dark', builtin, tokens }
```

`apply.ts` 遍历注册表，把每套主题编译成一段 `:root[data-theme='…'] { --mn-bg: …; }`，
拼成一张 `<style id="mn-theme">` 注入 `<head>`。换主题就是改 `documentElement.dataset.theme` 一个属性。

带来三件事：

1. 换主题不触发 React 渲染，也没有逐 token 的 JS 写入，浏览器只是换了一条 CSS 规则；
2. 用户主题（以后的主题编辑器、导入的主题）只要注册进 registry 就自动生效，不需要改代码或 CSS；
3. 加一套主题的成本 = 加一条数据。

`styles/app.css` 里用 Tailwind v4 的 **`@theme inline`** 把语义 token 接上：

```css
@theme inline { --color-bg: var(--mn-bg); … }
```

必须用 `inline`：值是 `var()` 引用，`inline` 才会把值内联进工具类（`bg-bg` → `background-color: var(--mn-bg)`）。
不用 `inline` 的话 Tailwind 会先在 `:root` 里把 `--color-bg` 固化成当时的颜色，运行时换主题就换不动了。
接上之后，书架、工具栏、弹窗、正文全部走同一组变量——换主题是整个 app 一起变，不会只换一半。

### 5.2 为什么不做成「组件里传 props / 写内联样式」

这是 koodo-reader 的做法，也是我们要避免的：它没有 CSS 变量，一个「主题」是两个裸字符串
（`{ key, textColor, backgroundColor, title }`），有四套并行机制——强调色生成 CSS 打在约 60 个
**手工维护的选择器数组**上、明暗皮肤靠换整个 `<link>` 样式表、阅读区用 React 内联样式、
正文 iframe 里注入拼接的 CSS 字符串。每加一个可主题化的界面，就要往那些数组里补类名。

变量级联不需要这个成本：新界面只要用现成的工具类就自动跟随主题。

### 5.3 阅读设置走同一套思路

字号、行距、字距、首行缩进、段间距、栏宽、对齐、字体栈都是 CSS 变量，写在阅读器容器上：

```
--mn-font-size / --mn-line-height / --mn-para-gap / --mn-indent / --mn-content-width / …
```

改动只是对一个元素 `style.setProperty`，正文 DOM 不重渲染，变量级联到从 EPUB 迁进来的 HTML 上。
这也是「一套排版管两种格式」能成立的原因：TXT 生成的 `<p>` 和 EPUB 迁进来的 XHTML 走同一组规则。

## 六、TXT：编码与分章

这一节是踩坑记录，因为这两件事的失败方式是「某本书正好没识别对」，最难靠肉眼发现。

### 6.1 编码检测的顺序是**先 UTF-16、再 UTF-8**

原本的顺序是 BOM → UTF-8 严格解码 → chardet → 兜底，验收脚本当场发现 UTF-16LE（无 BOM）被判成了 GB18030。

原因很隐蔽：**UTF-16LE 里的汉字是「低位字节 + 0x4E-0x9F」，而这些字节全都在合法 ASCII 范围内。**
`本` 是 U+672C → `2C 67` → 解成 `,g`；`书` 是 U+4E66 → `66 4E` → 解成 `fN`。
于是 UTF-16 的中文文本**能**通过 UTF-8 的严格解码，只是解出一堆看起来像正常 ASCII 的乱码，
`fatal: true` 这个本该救命的信号完全没响。

修法是加一个纯结构性的判据，而且排在 UTF-8 之前：

**判据一：换行的位置。** UTF-16 里换行是 `0A 00`（小端）或 `00 0A`（大端），
所以 `0x0A` 只会落在同一侧的字节位置上；而 UTF-8 文本里 `0x0A` 只来自换行，奇偶各半。
于是「`0x0A` 几乎全在偶数位」就是小端的强证据（阈值 0.05，且至少 8 个换行才判）。

这里有个中间版本的失败值得记下来：最初用的是「`0A` 后面是不是 `00`」的配对率。
实测比例只有 **0.71**，阈值定不下去——因为汉字 **「上」是 U+4E0A**，低位字节正好是 `0x0A`，
在正文里出现得极频繁，把配对率稀释了。改看**位置**（奇偶）就绕开了整个问题。

**判据二：高位字节大量为 0**，用于英文等 BMP 低码位的 UTF-16 文本。

最后还有一层 `looksLikeText()`（控制字符比例 < 2%）挡住「字节序猜反了」的情况。

### 6.2 自动检测不可能 100%，所以必须有手动覆盖

koodo-reader 的缺口也在这里：它用 chardet 看前 4096 字节，失败就退回 `"utf8"`，
而且**没有手动改编码的入口**（`charset` 字段存了但所有导入路径都传空值）。
短文件或者中英混排猜错时，用户没有任何办法。

我们的做法：检测结果 + 置信度 + 一句中文提醒写进书里，导入弹窗和「解析设置」都能改，
改完原地重新解析。自动检测永远会有例外，有个能改的入口比把猜测调得更花哨重要。

### 6.3 分章：逐级升级的模板 + 干扰项守卫

判定的是「这一行是不是标题」，而不是用一个正则切全文。模板逐级升级：

1. `第<数字>[章节節回话話集]` + 可选标题（数字支持中文/阿拉伯/全角）
2. `序章` / `楔子` / `引子` / `番外` / `尾声` / `后记` 这类固定篇名
3. `Chapter N` / `Part N`（英文小说）
4. 纯数字标题（`1.` / `十二、`）——**只在前三档命中少于 3 个时才启用**，这一档最容易把正文切碎

守卫条件（`isPlausibleTitle`）里最有效的两条是：长度 ≤ 40，以及**不含「。」**——
正文行几乎必然带句号，标题几乎不会。加上「不以逗号/分号结尾」兜住被截断的正文行。

验收样例里专门放了干扰项（`他翻到第一章的时候愣了一下，因为那一段被水浸过`、
`第 12 页上有一行批注`），断言它们必须留在正文里、不能变成标题。

**自动模式的探测是提前收工的**：扫到 3 个命中就认定这个规则可用，所以试三种规则几乎不花时间；
只有全都不命中时才会老实扫一遍（而且扫到 8MB 就停）。

### 6.4 卷/章层级

中文小说常见「第一卷 → 第一章」的两级结构。做法是：卷标题先不下结论，
**等下一行看是章节标题还是大段正文**——

- 后面跟的是章节标题 → 卷是目录分组，记成 `depth: 0` 的节点，那一行作为正文的居中标题并进首章；
- 卷标题之后攒了 ≥ 400 字还没出现章节标题 → 这个「卷」本身就是一章（有些网文就是卷里直接上正文）。

连续两个卷标题时，前一个卷的内容会被带上，不会丢字。

## 七、EPUB

### 7.1 章节归并：按目录目标切，不按 spine 切

很多 EPUB 把书切成几百个极小的 spine 文档（一个场景一个，甚至一段一个）。
按 spine 逐篇成章的话，目录里会出现 400 个「第 N 章」。

规则：**目录项落在哪个 spine 文档上，那里就是一个章节边界**；两个目录目标之间的连续文档合并进同一章。
目录项自带的层级当章节的缩进依据（压到 0-2 级），目录里没有链接的分组标题（nav 的 `<span>`、
ncx 的空 content）保留成 `groups` 里的卷节点。

验收样例刻意塞了一个不在目录里的 spine 文档，断言它必须并进上一章而不是自成章节。

### 7.2 净化分两层，而且不依赖单点

原计划只靠 DOMPurify。写 EPUB 验收时发现：**DOMPurify 在 happy-dom 下会静默什么都不做**——
不是配置问题，默认配置连 `<script>` 和 `javascript:` 都不处理。测试环境是这样，那真机环境会不会有
别的意外？把「正文不执行脚本」完全押在第三方库按预期工作上是没必要的风险。

于是改成两层：

1. **`scrubDocument()`**：我们自己删危险标签、`on*` 事件属性、危险协议。只依赖标准 DOM 接口，
   任何环境下的行为都一样。
2. **DOMPurify**：属性白名单、URL 校验、mXSS 这些深水区交给它。

验收脚本里加了一组恶意内容断言（script / iframe / object / onclick / `javascript:` 的 href 和 src），
现在在 happy-dom 下也是通过的——因为它验的是第一层。

### 7.3 「版式归我们，语义归书」

解析时剥掉书自带的一切样式：`<style>` / `<link>` / 全部 `class`，
内联 `style` 走白名单（只留 `text-align`、`font-style`、`font-weight`、`font-variant`、`text-decoration`），
带 `url()` 或尖括号的一律拒绝。

这是「一套主题管所有格式」能成立的前提。代价是**图文型 EPUB 的原始版式不保留**——
那需要一个单独的「保留原版式」开关，和统一主题是互斥的，留到以后单独设计。

### 7.4 图片与链接

- 图片：`src` 解析成 zip 内路径（处理 `../`、`%20`、大小写不匹配），重写成 `mnres://<path>`；
  远程图和 `data:` 原样保留；指向字体/音频之类（我们没抽出来的）则删掉属性，免得留一个坏请求。
- 跨章链接：解析成 `#mnref-<章号>:<锚点>`，由阅读器拦截后切章并滚到锚点——脚注就是这么工作的。
- 同章锚点：保留 `#fragment`，点击时在列布局里按 `offsetLeft` 换算出页码。

封面走回退链：`properties="cover-image"` → `<meta name="cover">` → `guide` 的 cover 页里的第一张图 → 文件名里带 cover 的图。
抽出来之后缩到 ≤400px 宽再存——书架上要显示的是缩略图，不是原图。

## 八、阅读器：滚动与翻页

### 8.1 为什么不做 iframe

koodo-reader 用 iframe 装正文，代价是 CSS 变量过不去（主题要注入第二份）、划词定位和搜索都更麻烦。
我们用净化 + 作用域 CSS 拿到隔离：既然书的样式已经被剥光了，冲突风险本来就被消除了。
以后真遇到某本书的 HTML 作乱，再包一层 Shadow DOM 即可。

### 8.2 翻页用 CSS 多列

列宽 = 一页宽度，`column-gap: 0`，于是「一列 = 一页」，总页数 = `scrollWidth / 列宽`，
翻页就是给内容做一次 `translateX`。`column-fill: auto` 是关键：内容按顺序填满一列再排下一列，
缺了它浏览器会把内容平均分到所有列里，翻页顺序就乱了。

验收时确认了 `scrollWidth` 确实会算上列的溢出（672 宽、2 页 → 1344），这一点原本只是推测。

### 8.3 测量为什么会失败，以及为什么要重试

翻页模式的所有几何都建立在「容器宽度」上，而这个值在你最需要它的时候可能是错的。踩过的两个坑：

**坑一：宽度为 0 时不能硬算。** 容器还没拿到宽度时，`clientWidth` 可能是元素自身的 padding（实测 32px）。
原来的代码有个 `Math.max(240, …)` 的下限兜底，于是页宽被兜成 240，正文被切成 16 列，
页数变成 16，`page` 被算到 15，`transform` 成了 `translateX(-3600px)`——而且因为没有尺寸变化，
`ResizeObserver` 不会再来纠正。现在的做法是**宽度不可信就这一拍什么都不做**，交给上层重试。

**坑二：一次测量不够。** 图片解码会改变列数（正文多出一列），字体就位也会。
修法是进入本章后反复测量，成功前每 250ms 试一次（最多 40 次），成功后每 200ms 再确认十几次然后收工。
**每次测量都以 `ratioRef` 为准**，所以重来只会收敛到正确位置，不会漂移。

### 8.4 `ratioRef` 是当前位置的唯一记录

这是验收时发现的真 bug：翻页只更新了 `page` 状态，没有更新 `ratioRef`。
于是翻完页再转屏（或改字号、改窗口大小）触发重新测量时，位置会跳回「进入本章时」的地方。

规则：**任何改变阅读位置的路径都必须同时更新 `ratioRef`**（翻页、跳锚点、拖进度条）。
少了这一行，症状是「翻了页，然后转一下手机，回到原位了」。

### 8.5 进度持久化

- 滚动时进度每 100ms 上报一次（限流，不然进度条每帧都在 setState）；
- 写库是 1 秒防抖——滚动期间定时器一直被推迟，所以真正的写入发生在「停下来 1 秒之后」；
- 另外监听 `visibilitychange`(hidden) 和 `pagehide` 兜底，手机上切走 App 不会丢位置。

## 九、PWA 与存储

- Workbox **只预缓存 app 外壳**（js / css / html / svg / png）。书一条都不进 precache——
  它在 IndexedDB 里，这本身就是离线能读的原因。`navigateFallback: index.html` 让任意路由离线都能打开。
- **第一次导入时申请 `navigator.storage.persist()`**。不申请的话，浏览器在存储紧张时可以把整个书库清掉——
  对一个「本地就是唯一副本」的应用来说这是灾难性的。设置面板里用 `estimate()` 显示占用。
- 开发时 `devOptions.enabled: false`：开着 SW 会让「改了没生效」变成常态。
- 图标从一张 `public/logo.svg` 由 `@vite-pwa/assets-generator` 生成全套（含 maskable 和 apple-touch）。

## 十、验收方式

house 里没有测试框架也没有 CI（MioNote 就是 `tsc --noEmit` + 手动跑）。但解析器这块不行：
编码识别、分章、目录归并、路径重写的失败方式是「某本书正好没识别对」，靠手动找文件来测覆盖永远不够。

所以有两个验收脚本：

```bash
bun run samples     # 生成样例（含一个手写的、刻意很脏的 epub）
bun run verify      # 37 项 txt 断言 + 36 项 epub 断言
```

- **`verify-parsers.ts`**（Bun 直跑）：UTF-8 / UTF-16LE / GB18030 / Big5 / 英文 / 无章节标记 /
  标题干扰项 / 手动编码覆盖 / 强制规则不被静默改写 / `charOffsets` 自洽。
- **`verify-epub.ts`**（happy-dom 顶一个最小 DOM）：元数据、章节归并、图片重写、样式剥除、
  ruby 保留、跨章与同章链接、卷节点、损坏文件的错误信息，以及一组恶意内容断言。

`make-samples.ts` 里那个最小 EPUB 是手写的（用 fflate 打包，连 PNG 都是自己编的），
里面刻意塞了真实书里会遇到的脏东西：章内 `<style>`、`class`、把图片撑到 9999px 的内联样式、
跨章脚注链接、不在目录里的凑数 spine 文档、ruby 注音。

**GBK / Big5 的样例不由脚本生成**：Node 和 Bun 的编码支持里没有 GB18030 输出，
强行手写字节序列只会写出自己都不确定的文件。用 Windows 的 936 / 950 代码页转（命令在脚本输出里）。
Big5 那份是把简体正文塞进 950 代码页，Big5 里没有的字会被替换成 `?`——
所以对它的断言只覆盖结构（多字节解码成功、分章正确），不断言具体文字。

浏览器端做过一次完整的交互验收：拖入 TXT 和 EPUB → 书架出现卡片（封面、字数）→ 进入阅读器
（正文、ruby、图片从 blob URL 加载成功）→ 切换夜间主题（`data-theme` 变化带动正文、工具栏、
`<meta name="theme-color">` 一起变）→ 切到翻页模式（列宽 672、页数正确、翻页推进章节）→
刷新后阅读模式、主题、进度都恢复 → 目录抽屉列出卷节点和每章字数。

离线能力也实测过（生产构建 + `bun run preview`）：Service Worker 激活后
precache 里有全部 14 个外壳资源（index.html、两个 JS chunk——**包括按需加载的解析器 chunk**、
CSS、图标、manifest）。书在 IndexedDB 里，所以在没有网络时「打开 app → 打开一本已导入的书」
这条路径上没有任何东西依赖网络。

## 十一、已知取舍

| 取舍 | 现状 | 以后怎么办 |
|---|---|---|
| 硬换行的英文 txt | 一行 = 一段，所以会变成一句一段 | 需要「合并软换行」选项：靠行长的聚簇程度和行尾标点比例判别，是个独立问题 |
| 整本塞进一个 spine 文档的 epub | 会变成一章 | 按文档内的 h1/h2 再切一次 |
| 图文型 epub 的原始版式 | 不保留（为了统一主题） | 单独的「保留原版式」开关，和主题互斥 |
| 大文件导入 | 主线程流式处理，靠分片让出事件循环 | 真出现卡顿就搬进 Worker |
| 全文搜索 | 没有 | 章节已按章存库，加 Worker 里线性扫描即可 |
| 主题 | 6 套内置 + 自定义 CSS 逃生口 | 主题编辑器（往注册表写数据即可，UI 是独立工作） |

## 十三、决定记录

### 17. 验收发现并修掉的问题（2026-09-22）

验收脚本和浏览器验收一共发现五个真问题，都记在上面相应章节里：

1. **UTF-16LE 被判成 GB18030** —— UTF-16 的中文能通过 UTF-8 的严格解码（六 6.1）。
2. **字符数把 HTML 标签也算进去了** —— 段数多的书百分比会偏（四 4.2）。
3. **卷目录项指错章** —— 收尾顺序让「前言」插在卷节点之前（六 6.4）。
4. **`<style>` / `<script>` 只靠 DOMPurify 挡** —— 它在某些 DOM 实现下是空转的（七 7.2）。
5. **翻页后 `ratioRef` 没更新** —— 重新测量时位置会跳回进本章时的地方（八 8.4）；
   以及连带的页宽测量失败没有重试（八 8.3）。

第 1、4、5 条都属于「不写验收就发现不了」的类型：功能看起来是好的，坏在边界上。
这也是为什么这个项目里有一个没有 CI 也要留的 `verify` 脚本。
